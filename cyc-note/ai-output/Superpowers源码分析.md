## 核心思路

Superpowers 用可组合的 `SKILL.md` 把软件开发过程写成编码代理能遵循的流程。文章以传统软件工程为线索，梳理了 14 项技能。入口技能负责检查当前任务适用的技能。作者以 Gemini CLI 为例，说明会话开始时加载技能元数据，有需要时通过 `activate_skill` 加载完整指令。

主流程从澄清需求和确认设计开始，随后建立隔离工作树、写实施计划，再进入实现、审查和验证，最后决定如何处理开发分支。

## 14 项技能速查

### 启动、设计与计划

| 技能 | 何时使用 | 检查点 |
| --- | --- | --- |
| `using-superpowers` | 会话开始 | 先判断适用技能。文中把用户明确指令放在技能规则之前。 |
| `brainstorming` | 需求尚需细化时 | 看现有项目，明确目的、约束和验收条件，比较方案并取得设计确认。 |
| `using-git-worktrees` | 需要隔离开发环境时 | 建立独立工作树，检查目录是否被忽略，安装依赖并验证测试基线。 |
| `writing-plans` | 已有设计或详细需求时 | 拆成可独立验证的小步骤，写明文件路径、改动内容和验证命令。 |

### 执行与并行

| 技能 | 何时使用 | 检查点 |
| --- | --- | --- |
| `subagent-driven-development` | 在当前会话中执行可拆分的计划时 | 每个任务交给新的子代理，先审查是否符合规格，再审查代码质量。 |
| `executing-plans` | 已有书面计划并按检查点推进时 | 执行前审查计划，逐项实现和验证，在检查点汇报结果。 |
| `dispatching-parallel-agents` | 多个问题可以独立处理时 | 按问题域划分范围。确认没有共享状态或先后依赖，集成后检验冲突并运行测试。 |

### 测试、调试与交付

| 技能 | 何时使用 | 检查点 |
| --- | --- | --- |
| `test-driven-development` | 实现功能、修复缺陷或改变行为时 | 先写一个行为测试，确认它因预期原因失败。用最小实现让它通过，再在测试保持通过的前提下重构。 |
| `systematic-debugging` | 测试失败或行为异常时 | 复现并收集证据，对比正常模式，提出可验证的假设并一次只改一个变量，最后针对根因修复。 |
| `verification-before-completion` | 声称已完成、修复或通过前 | 运行与声明相对应的验证命令，查看完整输出、退出码和失败项，再据实报告。 |
| `requesting-code-review` | 任务完成、重大功能完成或合并前 | 给审阅者计划和变更范围，按严重程度检查，先处理阻塞问题。 |
| `receiving-code-review` | 收到评审反馈时 | 对照当前代码库验证建议，澄清歧义，逐项处理并验证回归。 |
| `finishing-a-development-branch` | 实现完成、测试通过后 | 按用户选择本地合并、创建 PR、保留或放弃分支，再处理工作树。放弃需要确认。 |

### 编写技能

| 技能 | 何时使用 | 检查点 |
| --- | --- | --- |
| `writing-skills` | 创建或修改技能时 | 先在没有技能的情况下运行场景，记录失败表现，再写指令并复测。用新场景检验规则能否被正确发现和应用。 |

## 三种验证各自回答的问题

- **测试为什么失败？** 先确认测试能识别缺失的目标行为。测试因语法错误或测试环境问题而失败时，需要先修正测试条件。
- **缺陷发生在哪一层？** 系统化调试先记录各组件的输入和输出，追踪数据流。当多次修复仍然失败时，重新检查共享状态、耦合和架构假设。
- **什么证据支持交付结论？** 测试通过看失败数，构建成功看构建命令及退出码，缺陷修复看原始症状能否通过回归验证。需求是否覆盖还要逐项对照验收条件。

### 1. Superpowers 简介

Superpowers 是一套为你的编码Agent设计的完整软件开发工作流程，它建立在一系列可组合的“技能”和一些初始指令之上，这些指令确保你的Agent能够使用这些技能。Superpowers 像是一套为“AI 编程”准备的加强包：你在用 Claude、Codex、 [Cursor](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=Cursor&zhida_source=entity) ……这些 AI Coding Agent 时，都可以安装这套 Skills，来提升 Agent 的软件工程能力。

#### 1.1 工作原理

实际上 superpowers 不是单一的一个 Skill，而是由 14 个 Skill 组成的。本质上superpowers 是将传统软件开发的过程，“需求调研→设计方案→代码编写→Debug→代码测试→代码评审→生产部署”，提炼成一套由多个Skill构成的工作流，而这套工作流由编程智能体自动运行。

**图：传统的瀑布模型**

![](https://pic4.zhimg.com/v2-b554fa707150e16eb0356a4afaa8788b_r.jpg)

**有了Superpowers 以后的基本工作流程：**

1. **头脑风暴 (brainstorming)** - 在编写代码之前启动。通过提问细化粗略的想法，探索替代方案，分节展示设计以进行验证。保存设计文档。
2. **使用 Git 工作树 (using-git-worktrees)** - 在设计批准后启动。在新分支上创建隔离的工作区，运行项目设置，验证干净的测试基线。
3. **编写计划 (writing-plans)** - 在设计批准后启动。将工作分解为小任务（每个任务2-5分钟）。每个任务都有精确的文件路径、完整的代码和验证步骤。
4. **[子代理驱动开发](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=2&q=%E5%AD%90%E4%BB%A3%E7%90%86%E9%A9%B1%E5%8A%A8%E5%BC%80%E5%8F%91&zhida_source=entity) (subagent-driven-development)** 或 **执行计划 (executing-plans)** - 在计划制定后启动。为每个任务分派一个全新的子代理，进行两阶段审查（规范符合性，然后是代码质量），或通过人工检查点批量执行。
5. **测试驱动开发 ([test-driven-development](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=test-driven-development&zhida_source=entity))** - 在实施过程中启动。强制执行 RED-GREEN-REFACTOR：编写失败的测试，观察其失败，编写最少量的代码，观察其通过，提交。删除在测试之前编写的代码。
6. **请求代码审查 (requesting-code-review)** - 在任务之间启动。根据计划进行审查，按严重程度报告问题。关键问题会阻碍进展。
7. **完成开发分支 (finishing-a-development-branch)** - 在任务完成后启动。验证测试，提供选项（合并/拉取请求/保留/丢弃），清理工作树。

代理在执行任何任务之前都会检查相关技能。这些是 **强制性工作流程，而非建议** 。

#### 1.2 哲学理念

- **测试驱动开发 (Test-Driven Development)** 始终先编写测试。
- **系统化而非临时化 (Systematic over [ad-hoc](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=ad-hoc&zhida_source=entity))** 过程优先于猜测。
- **降低复杂性 (Complexity reduction)** 简单性是主要目标。
- **证据优于断言 (Evidence over claims)** 在宣布成功之前进行验证。

### 2. 深入理解 SKILL 体系

在 [Gemini CLI](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=Gemini+CLI&zhida_source=entity) 中：技能通过 activate\_skill工具激活。

Gemini 会在会话开始时加载技能元数据，并在需要时加载完整技能内容。

关于 activate\_skillactivate\_skill是一个指令或函数，它的作用是明确地告诉 Gemini 在当前会话中，哪些特定的技能是可用的。Gemini 并非默认知道所有可能的技能，用户（或系统配置）需要通过这个工具来“启用”它们。当你使用 activate\_skill工具时，你实际上是在向 Gemini 的运行时环境注册一个或多个技能。这个注册过程通常会传递技能的标识符（如名称）以及可能的一些配置信息。会话开始时加载技能元数据 (Metadata Loading at Session Start)什么是元数据？技能元数据是关于技能的高层描述信息，而不是技能本身的执行代码。它通常包括：技能的名称（Name）技能的简短描述（Description）：告诉 Gemini 这个技能是做什么的。技能的输入参数（Input Parameters）：调用这个技能需要哪些信息。技能的输出类型（Output Type）：这个技能会返回什么类型的结果。如何调用这个技能的“接口”信息（例如，一个函数签名或API端点）。

#### SKILL 1：using-superpowers

名称：using-superpowers描述：在开始任何对话时使用——用于建立如何查找和使用技能的方式，并要求在任何回复之前（包括澄清问题）必须调用 Skill 工具。

**核心规则** ：

如果你是作为子代理被派遣来执行某个特定任务，请跳过此技能。 **如果你认为某个技能哪怕只有 1% 的可能适用于当前任务，你绝对必须调用该技能。**

如果某个技能适用于你的任务，你没有选择权，你必须使用它。

这是不可协商的。这不是可选项。你不能通过任何理由绕过它。

**指令优先级**

Superpowers 的技能可以覆盖默认系统提示行为，但用户指令始终优先：

1. 用户的明确指令（CLAUDE.md、GEMINI.md、AGENTS.md、或直接请求）——最高优先级
2. Superpowers 技能——当与默认系统行为冲突时覆盖默认行为
3. 默认系统提示——最低优先级

**例如** ：

如果 CLAUDE.md、GEMINI.md 或 AGENTS.md 说“不要使用 TDD”，而某个技能说“始终使用 TDD”，那么应遵循用户的指令。用户拥有最终控制权。

#### SKILL 2：brainstorming

名称： [brainstorming](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=3&q=brainstorming&zhida_source=entity) 描述：“在进行任何创造性工作之前 必须 使用此流程——包括创建功能、构建组件、增加功能或修改行为。通过自然的协作对话，将想法探索为清晰的设计与规格说明。”

**理解这个概念** ：

- 首先查看当前项目状态（文件、文档、最近的提交）
- 在提出详细问题之前，请先评估项目范围：如果需求描述了多个独立的子系统（例如，“构建一个包含聊天、文件存储、计费和分析功能的平台”），请立即标记出来。不要把时间浪费在完善一个需要先分解的项目细节上。
- 如果项目规模过大，无法用单一规范来描述，则应帮助用户将其分解为多个子项目：哪些部分是独立的，它们之间有何关联，以及应该按什么顺序构建？然后，按照常规设计流程，集思广益地完成第一个子项目。每个子项目都有其自身的规范 → 计划 → 实施周期。
- 对于范围合适的项目，一次提出一个问题，以完善想法。
- 尽量选择题，但开放式问题也可以接受。
- 每条消息只提一个问题——如果某个主题需要更深入探讨，请将其拆分成多个问题。
- 重点在于理解： **目的、限制条件、成功标准**  
	**探索方法** ：
- 提出2-3种不同的方法，并说明每种方法的优缺点。
- 以对话的方式提出选项，并附上您的建议和理由。
- 首先提出你推荐的方案，并解释原因。  
	**设计方案展示** ：
- 一旦你确信自己理解了正在构建的内容，就可以展示设计方案了。
- 根据各部分的复杂程度调整篇幅：如果内容简单明了，几句话即可；如果内容微妙复杂，则最多可使用 200-300 字。
- 每节课后都要问问大家，目前为止看起来是否合适。
- 涵盖内容：架构、组件、数据流、错误处理、测试
- 如果有什么不明白的地方，要做好随时返回去澄清的准备。  
	**为隔离性与清晰度设计：**
- 将系统拆分成更小的单元，每个单元都有明确的目标，通过定义良好的接口进行通信，并且可以独立地被理解和测试。
- 对于每个单元，你应该能够回答：它的功能是什么，如何使用它，以及它依赖于什么？
- 不看内部代码，有人能理解一个单元的功能吗？能在不影响其他用户的情况下修改内部代码吗？如果不能，那么边界条件就需要改进。
- 更小、边界更清晰的单元也更容易处理——你可以更好地理解那些能够一次性掌握上下文的代码，而且当文件处于焦点状态时，你的编辑也更可靠。当一个文件变得很大时，这通常表明它执行了过多的操作。  
	**在现有代码库中工作** ：
- 在提出修改建议之前，先研究现有结构。遵循现有模式。
- 如果现有代码存在影响工作的问题（例如，文件过大、边界不清晰、职责混乱），则应在设计中纳入针对性的改进——这是优秀开发人员改进他们正在编写的代码的方式。
- 不要提出与当前目标无关的重构建议。始终专注于能够帮助实现当前目标的重构。

#### SKILL9：systematic-debugging

name: systematic-debuggingdescription: 在创建新技能、编辑现有技能或在部署前验证技能功能时使用。

**概述**

随意修复会浪费时间，并可能引入新的错误。快速补丁往往掩盖真正的问题。

**核心原则：** 始终先找到根本原因，再进行修复。只修复症状等同于失败。

违反该流程的字面规则，也就违反了调试的本质。

铁律在进行根因调查之前，不允许进行任何修复

**何时使用**

1. 系统化调试适用于任何技术问题，包括测试失败、生产 Bug、异常行为、性能问题、构建失败和系统集成问题。
2. 在高压力或高不确定性场景下尤其需要使用，例如时间紧迫、看似只需“小改动”、已尝试多次修复但失败、或对问题理解不充分。
3. 不要因为问题简单、时间紧急或被要求立即修复而跳过该过程，因为系统化调试通常比盲目尝试更快且更可靠。

**四个阶段**

你必须完成每个阶段才能进入下一个阶段。

| 阶段 | 目标 | 关键步骤 | 关键原则 |
| --- | --- | --- | --- |
| 阶段1：根因调查 (Root Cause Investigation) | 在任何修复前找到问题来源 | 阅读错误信息（完整 stack trace、行号、路径、错误码）；稳定复现问题；检查最近变更（Git diff、依赖、配置、环境）；在多组件系统中添加日志收集证据（记录组件输入/输出、环境传播、层状态）；运行一次定位故障层；追踪数据流直到找到源头 | 不调查根因，不允许修复；修复必须在源头而不是症状 |
| 阶段2：模式分析 (Pattern Analysis) | 通过对比找到异常差异 | 在代码库中寻找类似的正常实现；完整阅读参考实现而非略读；列出正常与异常实现的所有差异；分析依赖组件、配置和环境假设 | 在理解模式和差异之前不要修改代码 |
| 阶段3：假设与验证 (Hypothesis and Testing) | 使用科学方法验证原因 | 提出明确假设（“X 是根因，因为 Y”）；进行最小改动测试；一次只改变一个变量；验证结果；若失败则提出新假设；若不理解问题则继续研究或求助 | 避免多变量修改，保持实验可验证性 |
| 阶段4：实施修复 (Implementation) | 在确认根因后修复问题 | 先创建失败测试（最小复现、自动化或脚本）；实施单一修复；验证测试与系统是否正常；若修复失败则返回阶段1重新分析判断是否为架构问题：若已尝试 ≥3 次修复仍失败，则停止继续修补；分析是否存在共享状态、强耦合或系统性设计问题；评估是否需要架构重构；与团队讨论 | 修复必须针对根因且一次只做一个改动 |

**快速参考**

| 阶段 | 主要活动 | 成功标准 |
| --- | --- | --- |
| 根本原因 | 阅读错误、重现错误、检查更改、收集证据 | 理解“是什么”和“为什么”。 |
| 2\. 模式 | 查找实例，进行比较 | 找出差异 |
| 3\. 假设 | 形式理论，测试最少 | 已证实或新的假设 |
| 4\. 实施 | 创建测试、修复、验证 | 问题已解决，测试通过 |

1. 在声称任何状态或表达满意之前：
2. 识别： 什么命令可以证明这个声明？
3. 运行： 执行完整的命令（全新的，完整的）
4. 阅读： 完整输出，检查退出代码，计算失败次数
5. 验证： 输出是否确认了声明？
6. 如果否： 用证据说明实际状态
7. 如果是： 用证据说明声明
8. 只有在那之后： 做出声明
9. 跳过任何一步 = 撒谎，而不是验证

**常见失效**

| 声明 | 需要 | 不足之处 |
| --- | --- | --- |
| 测试通过 | 测试命令输出：0 失败 | 之前的运行，“应该通过” |
| [Linter](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=Linter&zhida_source=entity) 干净 | Linter 输出：0 错误 | 部分检查，推断 |
| 构建成功 | 构建命令：退出代码 0 | Linter 通过，日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码已更改，假定已修复 |
| 回归测试有效 | 红色-绿色循环已验证 | 测试通过一次 |
| 代理已完成 | VCS diff 显示更改 | 代理报告“成功” |
| 需求已满足 | 逐行检查清单 | 测试通过 |

**为什么这很重要：**

1. 未经验证的虚假完成会严重损害团队间的信任，并违反了“诚实”这一核心职业价值观。
2. 这直接导致交付包含未定义功能或缺失需求的产品，进而引发系统崩溃和功能不完整等严重问题。
3. 最终，这种行为会造成大量时间浪费在返工上，严重影响项目效率和交付质量。

**何时应用：**

1. 无论何时，在做出任何关于工作成功、完成或积极状态的声明，或表达满意情绪之前，都必须进行验证。
2. 这包括在提交代码、创建拉取请求（PR）、标记任务完成、转移到下一个任务或将工作委托给代理之前。
3. 该规则不仅适用于确切的短语，也适用于所有意译、同义词以及任何暗示成功或正确性的沟通形式。
4. 简而言之，任何可能传达工作已完成或正确的信息，都必须先经过严格的验证。

**总结**

验证没有捷径。运行命令。阅读输出。然后声明结果。这是不可协商的。

#### SKILL12：receiving-code-review

name: receiving-code-reviewdescription: 在接收到代码审查反馈时使用，在实施建议之前，特别是当反馈不明确或技术上存疑时——这需要技术严谨性和验证，而不是表面上的同意或盲目实施。

代码审查需要技术评估，而不是情感表演。

核心原则： 实施前验证。假设前提问。技术正确性优先于社交舒适度。

**响应模式**

1. 当收到代码审查反馈时：
2. 阅读： 完整阅读反馈，不作反应
3. 理解： 用自己的话复述要求（或提问）
4. 验证： 对照代码库的实际情况进行检查
5. 评估： 这对当前的这个代码库来说，技术上是否合理？
6. 响应： 技术性确认或有理有据的反驳
7. 实施： 一次只实施一项，并对每项进行测试  
	**禁止的响应**

| 绝不：“你完全正确！”（明确违反 CLAUDE.md）“说得好！”/“很棒的反馈！”（表演性质）“我这就去实现它”（在验证之前） | 而是：复述技术要求提出澄清问题如果有误，则用技术理由反驳直接开始工作（行动胜于言语） |
| --- | --- |

**处理不明确的反馈**

1. 如果任何项目不明确：
2. 停止——暂时不要实施任何东西
3. 就模糊不清的项目寻求澄清
4. 原因： 项目之间可能存在关联。部分理解 = 错误实施。
5. 示例：
6. 你的真人搭档：“修复 1-6”
7. 你理解 1,2,3,6。对 4,5 不清楚。
8. ❌ 错误： 现在实施 1,2,3,6，稍后再问 4,5
9. ✅ 正确： “我理解项目 1,2,3,6。在继续之前，需要澄清 4 和 5。”

**特定来源的处理**

1. 来自你的真人搭档
- 信任 - 理解后实施
- 如果范围不明确，仍然提问
- 不要表演性地同意
- 直接行动 或技术性确认

(b) 来自外部审阅者

1. 在实施之前：
2. 检查： 这对当前的这个代码库来说，技术上是否正确？
3. 检查： 是否会破坏现有功能？
4. 检查： 当前实现的原因是什么？
5. 检查： 是否适用于所有平台/版本？
6. 检查： 审阅者是否理解完整上下文？
7. 如果建议似乎有误：
8. 用技术理由反驳
9. 如果无法轻松验证：
10. 如实说明：“我无法在没有 \[X\] 的情况下验证这一点。我应该 \[调查/询问/继续\] 吗？”
11. 如果与你的真人搭档之前的决定冲突：
12. 先停止并与你的真人搭档讨论  
	你的真人搭档的规则： “外部反馈——持怀疑态度，但仔细检查。”

**YAGNI（你不需要它）检查“专业”功能**

1. 如果审阅者建议“正确实施”：
2. 在代码库中搜索实际用法
3. 如果未使用：“这个端点没有被调用。移除它（YAGNI）吗？”
4. 如果已使用：那么正确实施  
	你的真人搭档的规则： “你和审阅者都向我汇报。如果不需要这个功能，就不要添加。”  
	**实施顺序**

对于多项反馈：首先澄清任何不明确的项目然后按以下顺序实施：阻塞性问题（破坏、安全）简单修复（拼写错误、导入）复杂修复（重构、逻辑）逐个测试每个修复验证没有回归

**确认正确反馈**  
当反馈确实正确时：

1. ✅ “已修复。\[简要描述更改内容\]”
2. ✅ “抓得好——\[具体问题\]。已在 \[位置\] 修复。”
3. ✅ \[直接修复并在代码中展示\]
4. ❌ “你完全正确！”
5. ❌ “说得好！”
6. ❌ “谢谢你指出！”
7. ❌ “谢谢你 \[任何\]”
8. ❌ 任何表示感谢的表达  
	**为什么不感谢** ： 行动胜于言语。直接修复即可。代码本身就表明你听取了反馈。  
	**如果你发现自己即将写“谢谢”** ： 删除它。改为说明修复内容。

**优雅地纠正你的反驳**

1. 如果你反驳了但错了：
2. ✅ “你是对的——我检查了 \[X\]，它确实 \[Y\]。正在实施。”
3. ✅ “已验证，你是对的。我最初的理解是错误的，因为 \[原因\]。正在修复。”
4. ❌ 长篇道歉
5. ❌ 解释你为什么反驳
6. ❌ 过度解释  
	如实说明更正，然后继续。

**总结**

**外部反馈 = 需要评估的建议，而不是必须遵守的命令。**  
验证。提问。然后实施。不要表演性同意。始终保持技术严谨。

#### SKILL14：writing-skills

name: writing-skillsdescription: 在创建新技能、编辑现有技能或在部署前验证技能功能时使用。

writing-skills是将测试驱动开发应用于流程文档。  
个人skills存储在特定代理的目录中（Claude Code 的目录为 ~/.claude/skills，Codex 的目录为 ~/.agents/skills/）。

**什么是skills？**

技能是经过验证的技术、模式或工具的参考指南。技能可以帮助未来的 Claude 实例找到并应用有效的方法。  
**技能包括：** 可复用的技术、模式、工具和参考指南。  
**技能并非：** 讲述你曾经如何解决某个问题的叙述。

| Technique（技术）具有明确步骤的方法例如：condition-based-waitingroot-cause-tracing | Pattern（模式）一种思考问题的方式例如：flatten-with-flagstest-invariants | Reference（参考）API 文档、语法指南或工具文档例如：office 文档 |
| --- | --- | --- |

**SKILL.md 结构**

Frontmatter（ [YAML](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=YAML&zhida_source=entity) ）：必须包含两个字段：name和 description最大 1024 字符name：只能包含字母、数字和连字符description：第三人称只描述何时使用必须以 Use when...开头包含具体症状和场景绝不要总结技能流程

**示例：**

```
---
name: Skill-Name-With-Hyphens
description: Use when [specific triggering conditions and symptoms]
---
# Skill Name
## Overview
这是什么？核心原则 1–2 句话
## When to Use
如果决策不明显，可使用小型流程图
* 症状
* 使用场景
* 不适用场景
## Core Pattern

快速扫描的表格或列表

复杂参考链接外部文件

## Real-World Impact（可选）
实际结果
```

**Claude搜索优化（CSO）:**

1. **Description 决定 Skill 是否被发现：** 必须以 “Use when …” 开头，只描述触发场景或症状， **绝不能概括技能流程** ，否则 Claude 可能只执行 description 而跳过 Skill 正文。
2. **用问题和症状写触发条件：** 描述应体现问题本身（如 race condition、flaky test），而不是具体技术实现（如 setTimeout、sleep），并保持技术无关，除非技能本身是特定技术。
3. **覆盖 Claude 可能搜索的关键词：** 包含错误信息、症状词、同义词以及相关工具名或命令，提高 Skill 在检索时被命中的概率。
4. **命名要动词优先、语义清晰：** 使用动名词或动作表达（如 creating-skills、condition-based-waiting），名称应体现核心行为或洞见，而不是抽象类别。
5. **控制 Token 成本并避免冗余：** 保持 Skill 简短，细节放到工具帮助或引用其他 Skill，通过交叉引用、压缩示例和删除重复内容减少上下文消耗。

**流程图与代码示例：**

1. **流程图只用于表达决策逻辑，** 例如非显而易见的决策点、可能过早结束的循环流程，或“何时使用 A 而不是 B”的判断场景。
2. **不要用流程图表达信息或步骤：** 参考资料应用表格/列表，代码示例用代码块，线性流程用编号列表，并确保节点名称具有明确语义。
3. **代码示例遵循“一个优秀示例胜过多个普通示例”原则：** 示例应完整可运行、来自真实场景、清晰展示模式并解释原因，语言选择最相关的技术栈。
4. **避免示例泛化或膨胀：** 不要提供多语言实现、填空模板或人为设计的示例，一个高质量示例即可被迁移到其他语言或场景。

**测试所有技能类型：**

| 技能类型 | 示例 | 测试方法 | 成功标准 |
| --- | --- | --- | --- |
| 纪律执行技能（规则/要求） | TDD、完成前验证、编码前设计 | 学术问题（是否理解规则）；压力情境（压力下是否遵守）；多重压力测试（时间+沉没成本+疲惫）；设计反驳合理化理由 | 在最大压力下仍然遵循规则 |
| 技术技能（操作指南） | 基于条件的等待、根因追踪、防御性编程 | 应用场景（能否正确使用技术）；变体场景（能否处理极端情况）；信息缺失测试（说明是否完整） | 能够在新场景中正确应用该技术 |
| 模式识别技能（心智模型） | 降低复杂度、信息隐藏 | 识别场景（能否识别适用模式）；应用场景（能否正确应用）；反例测试（是否知道何时不适用） | 正确识别何时以及如何应用该模式 |
| 参考技能（文档/API） | API 文档、命令参考、库指南 | 检索场景（能否找到正确信息）；应用场景（能否正确使用）；覆盖测试（是否包含常见用例） | 能够找到并正确应用参考信息 |

**技能创建清单（TDD 改编版）**

**重要提示：** 请使用 TodoWrite 为以下每个清单项目创建待办事项。

| 阶段 | 任务类型 | 具体内容 |
| --- | --- | --- |
| 红色阶段（RED） | 编写失败测试 | 创建3种以上综合压力情境测试纪律技能；在无技能情况下运行场景并记录基线行为；识别失败中的合理化模式与问题模式。 |
| 绿色阶段（GREEN） | 编写基础技能 | 技能名称只使用字母、数字、连字符；提供包含 name 与 description 的 YAML 前置元数据（≤1024 字符）；说明以 “何时使用……” 开头并包含触发因素；使用第三人称描述；补充搜索关键词（错误、症状、工具）；提供清晰概述与核心原则；针对 RED 阶段发现的基线问题进行设计；代码直接嵌入或单独文件引用；提供一个高质量示例（非多语言）；运行场景验证技能是否生效。 |
| 重构阶段（REFACTOR） | 加固与完善 | 从测试中继续找出新的合理化理由；增加明确反制措施（适用于纪律技能）；根据测试迭代建立合理化表格；创建危险信号列表；持续测试并迭代直到稳定可靠。 |

**最终总结**

**创建 Skill 本质上是把 TDD 应用于流程文档。**

同样的铁律：没有失败的测试，就没有技能。同样的循环：红色（基线）→绿色（技能提升）→重构（堵塞漏洞）。同样的益处：更高的质量、更少的意外、万无一失的结果。

如果你在代码编写中遵循 TDD，那么在技能培养中也应该遵循 TDD。同样的原则也适用于文档编写。

### 3. Superpowers技能库

Superpowers 是一个技能库，这个技能库包含一系列skill：

- **协作 (Collaboration)**
- 头脑风暴 (brainstorming) - 苏格拉底式设计细化。
	- 编写计划 (writing-plans) - 详细的实施计划。
	- 执行计划 (executing-plans) - 带检查点的批量执行。
	- 分派并行代理 (dispatching-parallel-agents) - 并发子代理工作流。
	- 请求代码审查 (requesting-code-review) - 预审查清单。
	- 接收代码审查 (receiving-code-review) - 回应反馈。
	- 使用 Git 工作树 (using-git-worktrees) - 并行开发分支。
	- 完成开发分支 (finishing-a-development-branch) - 合并/拉取请求决策工作流。
	- 子代理驱动开发 (subagent-driven-development) - 带有两阶段审查（规范符合性，然后是代码质量）的快速迭代。

**测试 (Testing)**

- 测试驱动开发 (test-driven-development) - RED-GREEN-REFACTOR 循环（包括测试反模式参考）。

**调试 (Debugging)**

- 系统调试 (systematic-debugging) - 4阶段根本原因处理流程（包括根本原因追踪、深度防御、基于条件的等待技术）。
	- 完成前验证 (verification-before-completion) - 确保问题确实已修复。

**元 (Meta)**

- 使用超能力 (using-superpowers) - 技能系统介绍。
	- 编写技能 (writing-skills) - 遵循最佳实践创建新技能（包括测试方法论）。

| 技能名称 | 触发时机 | 核心功能 | 关键原则 |
| --- | --- | --- | --- |
| using-superpowers | 任何对话开始时 | 技能系统入门，告诉 AI 在做事前先检查适用技能 | 用户指令 > 技能 > 默认系统提示 |
| brainstorming | 任何创造性工作之前 | 通过 [苏格拉底式对话](https://zhida.zhihu.com/search?content_id=272320373&content_type=Article&match_order=1&q=%E8%8B%8F%E6%A0%BC%E6%8B%89%E5%BA%95%E5%BC%8F%E5%AF%B9%E8%AF%9D&zhida_source=entity) 将想法转化为设计和规格 | 先设计再编码，展示设计并获批准后才能实现 |
| using-git-worktrees | 开始功能工作或执行计划前 | 创建隔离的 Git 工作树，设置依赖，验证测试基线 | 系统化目录选择 + 安全验证 = 可靠隔离 |
| writing-plans | 有多步骤任务规格时，接触代码前 | 编写详细实现计划，包含精确文件路径、代码、验证步骤 | 每个任务 2-5 分钟，DRY、YAGNI、TDD、频繁提交 |
| subagent-driven-development | 在当前会话执行实现计划时 | 为每个任务派遣新子代理，两阶段评审（先规格后质量） | 新子代理/任务 + 两阶段评审 = 高质量、快速迭代 |
| executing-plans | 有书面计划需在单独会话执行时 | 加载计划、批判性评审、执行所有任务、完成时报告 | 严格按计划步骤执行，验证前不跳过 |
| dispatching-parallel-agents | 面对 2+ 独立任务时 | 为每个独立问题域派遣一个代理，并发工作 | 一个代理/独立问题域，让它们并发工作 |
| test-driven-development (TDD) | 实现任何功能或 bug 修复时 | 红-绿-重构循环：先写失败测试，看着失败，写最小代码通过 | 没有先失败的测试就没有生产代码 |
| systematic-debugging | 遇到任何 bug、测试失败或意外行为时 | 四阶段调试：根因调查 → 模式分析 → 假设测试 → 实现 | 没有先根因调查就没有修复 |
| verification-before-completion | 声称工作完成、修复或通过时 | 运行验证命令，阅读输出，然后才能声称完成 | 证据在前，声称在后，始终验证 |
| requesting-code-review | 完成任务、实现主要功能或合并前 | 派遣代码评审子代理在问题级联前捕获问题 | 早评审，常评审 |
| receiving-code-review | 接收代码评审反馈时 | 技术评估而非情感表现，验证前不实现 | 实现前验证，假设前询问，技术正确性高于社交舒适 |
| finishing-a-development-branch | 实现完成、所有测试通过时 | 验证测试，展示 4 个选项，执行选择，清理工作树 | 验证测试 → 展示选项 → 执行选择 → 清理 |
| writing-skills | 创建新技能、编辑现有技能或部署前验证时 | 将 TDD 应用于流程文档，先基线测试再写技能 | 没有先失败测试就没有技能 |
