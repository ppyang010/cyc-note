# JDK 21 → 25：虚拟线程为什么落地慢？

> [!info] 来源与整理范围
> - **作者**：三界小书生。
> - **原文**：[知乎回答](https://www.zhihu.com/question/1963249539436766749/answer/2093631769111163960)。
> - **整理日期**：2026-10-14；本次读取未提取到可靠的原文发布、修改时间。
> - **记录方式**：先提炼作者观点，再用 OpenJDK 官方文档核对关键技术事实；末尾保留目标回答原文，不混入推荐回答。
> - **阅读边界**：这是对“落地为什么慢”的工程分析，不是对 Java 社区热度或生产采用率的统计证明。

## 一句话结论

**虚拟线程降低的是阻塞等待时占用平台线程的成本，不是 CPU 计算、数据库查询或下游服务的成本。企业是否迁移，取决于真实瓶颈、资源治理、生态兼容性与上线收益，而不只是新 API 是否可用。**

## 1. 作者的核心观点

以下是对作者论证的概括，不代表其中所有案例、数字均已核实。

### 1.1 企业采用新特性的主要障碍是工程节奏

- 企业后端升级 JDK、依赖库和监控工具，需要兼容性验证、压测、灰度与回滚方案。
- 传统线程池方案已经够用时，新特性的收益不一定覆盖迁移和故障排查成本。
- 作者把早期 `pinning` 风险和第三方库适配，视为虚拟线程落地缓慢的重要原因。

### 1.2 排队变便宜，不代表瓶颈消失

原文举例：数据库连接池只有 50 个连接，即使大量请求改用虚拟线程等待，也不会凭空得到更多数据库处理能力。

关键区别：

- **释放载体线程**：虚拟线程阻塞时，运行时可以让平台线程执行其他虚拟线程。
- **释放业务资源**：数据库连接、事务、锁等仍由应用和对应组件的生命周期管理；不会因为虚拟线程卸载而自动释放。
- 如果尚未拿到数据库连接，等待者并未持有该连接；如果已经持有，则要按 JDBC、事务和连接池约定显式关闭、归还。

因此，要先区分“请求在等可用线程”与“请求在等数据库、连接池或下游服务”。后者不会仅靠换线程模型得到解决。

### 1.3 线程池承担的不只是线程复用

现有系统通常把这些职责绑在一起：

| 职责 | 传统方案 | 采用虚拟线程后仍需考虑 |
| --- | --- | --- |
| 执行任务 | 平台线程池 | 每个任务一个虚拟线程，仍可使用 `ExecutorService` |
| 限制下游并发 | 限定工作线程数 | 按资源配置 `Semaphore` 或其他并发闸门 |
| 过载处理 | 有界队列、拒绝策略 | 入口准入、超时、等待上限与拒绝策略 |
| 业务隔离 | 不同业务使用不同池 | 不同资源预算、并发闸门与独立监控 |
| 生命周期管理 | 关闭线程池、等待任务 | 关闭执行器、取消任务、传播超时与中断 |

> [!warning] 并发控制不等于 QPS 限流
> `Semaphore` 限制的是同时执行的操作数，并不自动限制每秒请求量，也不自动限制等待者总数。虚拟线程便宜，但等待中的请求、上下文和调用栈仍占内存；不能把无限排队当作过载保护。

### 1.4 适用场景不同，不存在一刀切替代

- **值得优先评估**：高并发、阻塞式网络 I/O 多、平台线程成为主要限制的服务。
- **收益可能有限**：瓶颈已经集中在数据库、少量连接或下游额度的系统。
- **继续使用平台线程池合理**：CPU 密集计算，以及已有成熟资源治理、改造收益不明确的任务。
- 成熟的异步、响应式实现也不必只因虚拟线程出现而全部重写。

## 2. 技术事实核对与勘误

> [!warning] 不要直接把原文当作技术手册
> 原文的工程取舍思路有参考价值，但包含 API 状态、工具时间线等明确误述，以及缺少可追溯出处的性能与采用率数字。

### 2.1 JDK 21 → 25 的准确时间线

| 版本 | 正式发布日期 | 与本文相关的事实 |
| --- | --- | --- |
| JDK 21 | 2023-09-19 | 虚拟线程正式发布，见 JEP 444；已包含相关 JFR 事件和新线程转储 |
| JDK 24 | 2025-03-18 | JEP 491 消除 `synchronized` 导致的主要 pinning 场景 |
| JDK 25 | 2025-09-16 | 多数厂商的 LTS 版本；`ScopedValue` 正式发布；结构化并发仍为第五次预览 |

原文“JDK 21 到 23 这三年”“隔了整整三年”不准确：从 JDK 21 正式发布到 JDK 24 约一年半，到 JDK 25 约两年。

依据：[JDK 21](https://openjdk.org/projects/jdk/21/)、[JDK 24](https://openjdk.org/projects/jdk/24/)、[JDK 25](https://openjdk.org/projects/jdk/25/)。

### 2.2 `pinning` 必须按 JDK 版本讨论

- **JDK 21–23**：持有 `synchronized` 监视器时执行阻塞操作，可能无法卸载虚拟线程，连带阻塞载体线程。频繁、长时间的 pinning 会降低可扩展性；在特定锁和资源依赖下还可能导致饥饿或死锁。
- **JDK 24/25**：JEP 491 改变了监视器实现，虚拟线程可在持有监视器、等待获取监视器以及 `Object.wait()` 时卸载；不能继续把 `synchronized` 当作普遍的 pinning 原因。
- **仍有边界**：原生代码、外部函数回调及部分类加载、初始化等场景仍可能阻塞或 pin 住载体，不能理解为“所有阻塞都已解决”。
- **锁竞争依然存在**：解除 pinning 不会让互斥锁内的业务变成并行执行。应缩小锁范围，尽量避免持锁做长耗时 I/O。

载体调度器的默认**并行度**是 JVM 可见的可用处理器数，可配置；它不是任何条件下都固定不变的线程总数。原文“8 核钉 8 个就全瘫”是条件化的风险示例，而非所有应用必然发生的结果。

依据：[JEP 444](https://openjdk.org/jeps/444)、[JEP 491](https://openjdk.org/jeps/491)。

### 2.3 JDK 25 并没有把结构化并发转正

- `ScopedValue`：JDK 25 正式发布，见 **JEP 506**。
- `StructuredTaskScope`：JDK 25 仍属于**第五次预览 API**，见 **JEP 505**；使用时需要相应预览配置，并承担后续 API 变化风险。
- `Semaphore` 不是 JDK 25 才出现的能力；JEP 444 已推荐用它限制有限资源的并发访问。
- 使用虚拟线程不强制依赖 `ScopedValue` 或 `StructuredTaskScope`，也不要求放弃 `ExecutorService`、`Future` 等既有 API。

依据：[JEP 505](https://openjdk.org/jeps/505)、[JEP 506](https://openjdk.org/jeps/506)、[JEP 444](https://openjdk.org/jeps/444)。

### 2.4 JDK 21 已具备虚拟线程诊断工具

原文“JDK 21 只有 `tracePinnedThreads`，JDK 24 才补上 JFR 和 JSON 转储”不成立。

JEP 444 已明确包含：

- `jdk.VirtualThreadPinned` JFR 事件：默认启用，默认阈值为 20 ms；事件记录需运行 JFR。
- 新式线程转储：`jcmd <pid> Thread.dump_to_file -format=json <file>`。
- 虚拟线程调试、堆栈与相关诊断支持。

同时需要注意：

- 传统 `jstack` / `Thread.print` 转储**未扩展为列出全部虚拟线程**，不是简单地“输出太多看不清”。
- 新线程转储支持虚拟线程，但不包含传统转储中的全部锁等信息。
- JEP 491 移除了 `jdk.tracePinnedThreads` 属性；JDK 24 起设置它不再生效。剩余 pinning 的诊断应使用 JFR 等适当工具。
- APM、日志 MDC、链路上下文是否正常，要按具体工具版本与调用路径验证；不能泛化为“虚拟线程会普遍丢 traceId”。

依据：[JEP 444：观测与 JFR](https://openjdk.org/jeps/444)、[JEP 491：诊断变化](https://openjdk.org/jeps/491)。

### 2.5 不池化虚拟线程，仍是官方设计建议

JEP 444 明确推荐：**每个任务创建一个虚拟线程，不通过池化虚拟线程来限制并发；有限资源用信号量等机制控制。**

原文关于“官方承认池化更好”的表述未给出可追溯邮件链接，本笔记不将其记为已验证事实。

尤其不能把“每个任务创建一个虚拟线程”理解成“每个任务都新建一个平台线程”：虚拟线程本来就由运行时调度到可复用的载体线程上。个别基准结果也必须核对资源限制、等待策略和负载条件，不能直接推广为通用建议。

依据：[JEP 444：不要池化虚拟线程](https://openjdk.org/jeps/444#Do-not-pool-virtual-threads)。

### 2.6 不需要全面替换 `ThreadLocal` 或 `synchronized`

- 虚拟线程支持 `ThreadLocal`；挂载到不同载体时，线程局部变量仍属于逻辑上的虚拟线程。
- 需要警惕的是大量线程各自分配大对象，以及用 `ThreadLocal` 缓存昂贵资源的旧模式。另起子任务时的上下文传播，需要单独设计和验证。
- `ScopedValue` 适合有界作用域内的单向、不可变上下文绑定，并不是所有 `ThreadLocal` 用法的机械替代品。
- JDK 24/25 不需要仅为避免 `synchronized` pinning 而全量改成 `ReentrantLock`；按锁语义、灵活性和竞争情况选择。

依据：[JEP 444](https://openjdk.org/jeps/444)、[JEP 506](https://openjdk.org/jeps/506)、[JEP 491](https://openjdk.org/jeps/491)。

## 3. 迁移时可以直接使用的检查清单

以下为整理后的实践建议，不是原文逐字摘录。

- [ ] **测量真实瓶颈**：记录基线吞吐、P95/P99、CPU、内存、平台线程、连接池等待和下游延迟。
- [ ] **区分负载**：优先对阻塞等待型任务试点；CPU 密集工作使用明确的计算并发预算。
- [ ] **按版本排查**：JDK 21–23 重点检查长时间 `synchronized` + 阻塞；JDK 24/25 不盲目替换全部锁，仍关注原生调用和锁竞争。
- [ ] **保留资源治理**：数据库、HTTP、Redis 等各自配置连接预算、并发上限、超时与过载拒绝。
- [ ] **限制等待总量**：只加 `Semaphore` 不足以控制全部积压请求，仍需入口准入和等待期限。
- [ ] **审查上下文与内存**：验证日志 MDC、traceId、事务和安全上下文；避免每个虚拟线程持有大缓存。
- [ ] **验证故障场景**：慢查询、下游延迟、连接池耗尽、取消、中断、优雅关闭及峰值积压都要压测。
- [ ] **准备灰度与回滚**：在同等资源约束下对比旧实现，只有收益与可观测性达标后再扩大范围。

原文配置中的 `treu` 是拼写错误，应为：

```properties
spring.threads.virtual.enabled=true
```

具体生效范围仍需核对所用 Spring Boot 版本和执行器配置，不把这一开关理解成“所有任务自动迁移且无需治理”。

## 4. 值得记住的认知

1. **更多可等待的请求 ≠ 更多下游处理能力。**
2. **虚拟线程不是更快的线程，而是更便宜的并发单元。**
3. **执行模型与资源治理应分开设计：线程便宜了，并发预算和背压仍不能消失。**
4. **“不采用”可能是合理取舍，但“永远没用”与“升级即大幅提速”都不成立。**
5. **JDK 版本、依赖版本与工具版本会改变结论；不要用早期风险直接推断 JDK 25 的行为。**

> spring.threads.virtual.enabled=treu
>
> 前不久才开始的，之后不久就回滚了。
>
> 虚拟线程最大的坑，叫pinning，写 `synchronized` 块里调了个HTTP接口，虚拟线程在阻塞那一刻不会被卸载，而是死死钉在载体线程上。
>
> 载体线程池默认就是CPU核数，8核机器上钉8个，整个调度就瘫了。
>
> OpenJDK的loom-dev邮件列表里有一个案例：Spring Boot开了虚拟线程，底层Feign客户端连接池只有20个连接，21个并发请求就能让应用冻结，连接池耗尽后，后续请求等连接释放，而等连接的虚拟线程恰好进入了`AbstractConnPool.getPoolEntryBlocking()`里的`synchronized`区域，全部被钉住，载体线程一个不剩。
>
> HikariCP的issue #2293里更具体：HikariPool初始化时`getConnection`方法上的`synchronized`，配合Logback的`ReentrantLock`，10个载体线程里9个被钉在`synchronized`上，剩下1个park在载体线程上等锁，全灭。
>
> 你可能会说，那我不用`synchronized`不就行了？
>
> 这还真不行，HikariCP、Feign、旧版JDBC驱动，里面到处是`synchronized`。
>
> 无法把每一行代码都改成`ReentrantLock`，那些是别人的代码。
>
> 所以JDK 21到23这三年，虚拟线程对生产团队来说，基本是跑demo可以，上线别碰的状态。
>
> 这个问题到JDK 24的JEP 491才从根上解决，允许持有monitor的虚拟线程在阻塞时被卸载，而JDK 24不是LTS，真正大规模升级要等JDK 25。
>
> **时间线上看，虚拟线程从能用到敢用，中间隔了整整三年。**
>
> ![](https://picx.zhimg.com/50/v2-ecab44d24ca5750bb1b9ad0dbd1be3c1_720w.jpg?source=2c26e567)
>
> 虚拟线程解决的问题是：OS线程太贵，一个请求占一个线程，并发上不去，它让你可以用一个请求一个虚拟线程的写法，撑到很高的并发。
>
> 一个典型的Java后端服务，数据库连接池配置通常是10到50个连接。
>
> 你的请求打到数据库，连接池就是瓶颈。
>
> 虚拟线程让100万个请求同时挂起等待，但连接池里只有50个连接在真正干活，剩下的全部在排队，只是把排队的地方从线程池的队列换到了连接池的等待队列。
>
> 官方邮件列表里有一段讨论说得非常直白：大多数数据库连接池的实现会被限制在很小的连接数，虚拟线程会阻塞在队列上等待连接释放，这本身是正常的，但它并不能加速数据库。
>
> Stack Overflow上有个提问者问得很到位：“虚拟线程被说成是JDBC阻塞问题的银弹，但它真的能解决连接池有限的瓶颈吗？当虚拟线程向数据库发请求并挂起时，JDBC连接会被释放给其他请求吗？”
>
> 答案是不能，JDBC连接在虚拟线程挂起时依然被持有，虚拟线程卸载了载体线程，但没释放数据库连接。
>
> 所以如果你的服务瓶颈在下游，数据库、Redis、第三方API，虚拟线程带来的吞吐提升非常有限，它改善的是应用层扛并发的能力，不是下游的物理吞吐。
>
> 官方邮件列表里有人做过实验，发现 **池化虚拟线程的吞吐量反而比非池化高** ，因为在载体线程不足时，池化避免了反复创建平台线程的开销。
>
> 这直接打脸了永远不要池化虚拟线程的教条，官方后来也承认，池化虚拟线程在某些场景下可能有益，只是不推荐作为默认策略。
>
> **教条和现实打架的时候，现实赢。**
>
> 线上服务用传统线程池，出问题了，`jstack`一打，线程名、状态、堆栈全在，一眼看出哪里堵了。虚拟线程呢？几万个虚拟线程，`jstack`打出来的东西根本没法看。
>
> JDK 21的排查手段只有一个`-Djdk.tracePinnedThreads=full`，输出到stdout，生产环境你敢开？JDK 24才补上了`jfr print --events jdk.VirtualThreadPinned --stack-depth 100`这样的正经工具，还有`jcmd Thread.dump_to_file -format=json`。JFR对虚拟线程pinning事件的支持、JMC对虚拟线程调度器的可视化，都是后来才慢慢补齐的。
>
> 更别说APM了，你用的SkyWalking、Pinpoint、Arthas，对虚拟线程的支持到什么程度？很多监控工具在虚拟线程场景下，线程上下文传递是断的，traceId跟丢是常态，你花大力气改造上线，结果出了问题排查成本翻倍，ROI算不过来。
>
> 写Java写了十年的人，对线程池的感情是信任。
>
> 线程池帮你做了什么？限流，队列满了走拒绝策略；监控，活跃线程数、队列深度一目了然；资源隔离，不同业务用不同池子互不影响；优雅关闭，`shutdown()`之后等任务跑完。
>
> 虚拟线程说这些都别用了，用`Semaphore`限流，用`ScopedValue`传上下文，用`StructuredTaskScope`管生命周期。
>
> 这些东西在JDK 25才正式落地，而且你用的框架Spring、MyBatis、各种中间件客户端，有多少已经适配了？
>
> ![](https://picx.zhimg.com/50/v2-0ccb8b02263d5dff3a6e6ed913b2b7b0_720w.jpg?source=2c26e567)
>
> Apache Camel的issue里有一段很能说明问题：他们搞了个`ContextValue`抽象层，JDK 17到24用`ThreadLocal`，JDK 25+用`ScopedValue`。五个核心用法才迁移完。
>
> 一个主流框架的适配都要花这么大力气，你指望业务团队自己去改？
>
> 2025年有个调查说，十个Java后端里九个没在生产环境开过虚拟线程，剩下那个开了的，大概率正在排查一个诡异的线程阻塞问题。这话刻薄了点，但基本是事实。
>
> 不过也有数据在变，有生产实践报告显示，淘宝某系统从约2万个平台线程迁移到150万虚拟线程，吞吐提升75倍。
>
> Netflix的账单服务从8000线程到80万虚拟线程，提升100倍。这些案例的共同点是： **I/O极度密集，下游不是数据库连接池这种硬瓶颈，而是网络调用、文件IO这种可以真正并行等待的场景** 。
>
> 所以虚拟线程不是没用，是它的适用面比宣传的窄得多，它适合的是：你的服务本身是I/O等待型，下游瓶颈不集中在少数几个连接上，而且你有能力改掉代码里那些`ThreadLocal`和`synchronized`。
>
> 三个条件同时满足的团队，不多。
>
> 虚拟线程是JDK历史上最重要的特性之一，但它的落地周期会被严重低估，JDK 25是LTS，JEP 491修了pinning，`ScopedValue`和`StructuredTaskScope`都转正了，工具链也在补，接下来一两年，新项目会用虚拟线程作为默认选项，老项目会逐步迁移。
>
> 但线程池不会死，CPU密集型任务、需要严格资源隔离的场景、需要池化带来的监控和限流能力的场景，平台线程池依然是最合理的选择。
>
> 虚拟线程要淘汰的不是线程池，是 **用线程池来处理I/O阻塞这个在过去二十年被当成标准答案的模式** 。
>
> 至于为什么现在还没热起来，因为大家都很忙，谁也不想当那个在生产环境踩了pinning、半夜被叫起来rollback的人， **等JDK 25铺开，踩过坑的人把经验写进博客和文档，下一代新人上来的时候，虚拟线程才会真正变成默认。**
