## 一句话理解

普通对象的循环依赖，两级缓存就能解开。Spring 多出来的第三级，不是为了再存一份对象，而是把「要不要提前生成 AOP 代理」推迟到真的有人回头要这个 Bean 的时候。

## 作者的论证

作者把常见口诀拆开重推了一遍：一级放成品、二级放半成品、三级放工厂。口诀本身解释不了「去掉第二级或第三级行不行」。

### 没有 AOP 时，两级就够

假设 A 依赖 B，B 又依赖 A，而且都是普通 Java 对象。

1. A 先被反射创建出来，这时还是空壳，放入二级缓存。
2. A 发现需要 B，B 同样先创建半成品并放入二级缓存。
3. B 填属性时需要 A，一级缓存没有，二级缓存有，于是拿到 A 的引用。
4. B 走完生命周期后进入一级缓存；A 再拿回完整的 B，也进入一级缓存。

这一路没有用到第三级。作者由此认为，两级缓存完全能处理普通对象的循环依赖。

### AOP 把代理时机提前了

正常顺序是：实例化、注入依赖、初始化。AOP 代理通常在初始化阶段由 `BeanPostProcessor` 生成，Spring 希望流程走完后再把代理交出去。

循环依赖打破了这个顺序。若 A 最终应该以代理对象对外，而 B 在 A 初始化完成前就要 A，B 不能拿到原始对象。否则 B 留下的是原始引用，容器里后来放的是带事务和切面的代理，同一个 A 就会有两套对外引用。

只用两级也能硬做：A 刚 `new` 出来就判断要不要代理，要就立刻生成，再放进二级缓存。作者认为 Spring 不愿意为了兼容循环依赖，把所有需要代理的 Bean 都提前生成代理，哪怕它们根本没有循环依赖。

### 第三级只在真正需要时才生成早期引用

第三级放的不是 A 本身，而是一个 `ObjectFactory`，也就是一段先存起来、需要时才执行的逻辑。

A 实例化后，Spring 把「取得 A 早期引用」的工厂放进第三级，此时并不生成代理。A 继续注入 B：

- B 没有回头找 A：工厂不会被调用，A 仍按正常流程完成注入和初始化。
- B 真的需要 A：一级、二级都没有，于是调用工厂的 `getObject()`。需要代理时，就在这里提前处理。

取出的早期引用随后进入二级缓存，第三级里的工厂被移除。

### 第二级用来保证拿到同一个对象

如果只有第三级，B 触发工厂后，创建过程中 C 再来找 A，就会再执行一次工厂。作者认为这样无法保证 B 和 C 拿到同一个对象。

所以第一次取出的早期引用要放进二级缓存。C 再来时直接复用，不再执行工厂。

## 三级各自做什么

| 缓存 | 作者给出的职责 |
|---|---|
| 一级 | 放创建完成的 Bean |
| 二级 | 放已经提前暴露、后面要反复复用的早期引用 |
| 三级 | 放获取早期引用的工厂，把「要不要提前取出」留到真有人需要时再决定 |

作者的收束是：三级缓存不是因为两级处理不了普通循环依赖，而是还要顾及 AOP 代理的生成时机。能走正常流程的 Bean 就走正常流程；碰到循环依赖，才由第三级提前取出引用，再由第二级保证后续拿到的是同一个对象。

## 阅读时要注意的边界

- 这是作者自己的设计推演，页面上没有贴 Spring 源码，本次也没有对照源码核验。
- 「半成品」「工厂」是解释用语。源码里对应的是早期引用和 `ObjectFactory`，不是三份相同的对象缓存。
- 作者把第三级的必要性主要归结为 AOP 代理时机，并明确说这是对循环依赖这种不太好的设计所做的妥协。这个判断是观点，不是 Spring 官方表述。
