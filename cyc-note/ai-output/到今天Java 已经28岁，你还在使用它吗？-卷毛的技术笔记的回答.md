# 到今天Java 已经28岁，你还在使用它吗？你有什么故事想分享的？对Java未来发展有什么想说的？

> [!info] 来源信息
> - **作者**：卷毛的技术笔记
> - **来源**：[知乎回答](https://www.zhihu.com/question/602191439/answer/2085307388496713142)
> - **抓取日期**：2026-09-21
> - **核心主题**：JDK 27 紧凑对象头（Compact Object Headers / JEP 534 / Lilliput 项目）实战体验与性能分析

---

上周四晚上，我把测试环境里一个跑了半年的 Spring Boot 服务从 JDK 25 升到了 JDK 27。没动一行业务代码，没碰 JVM 参数，甚至没重启 Prometheus。

服务重启后我习惯性地切到 Grafana 面板，准备看一波 OOM 告警。结果等了十分钟，不仅没告警，堆内存水位线直接往下掉了一大截。QPS 没变，P99 响应时间没变，但 GC 频率从每分钟 3 次硬生生压到了不到 1 次。

这不是什么玄学调优，也不是我运气好碰上了低峰期。这是 JDK 27 里 **JEP 534（紧凑对象头）**在背后默默发力。

查了下官方 SPECjbb2015 的跑分数据：**堆内存减少 22%、CPU 时间减少 8%、GC 次数减少 15%**。Amazon 在生产环境几百个服务上验证过，SAP 也直接在自己的 SapMachine 里默认开启了。

这大概是 JDK 27 九个 JEP 里唯一一个**“默认开启、零成本、立即受益”**的特性。下面这篇笔记，是我这次升级前后摸到的所有细节，包括那些差点让我翻车的地方。

---

### 先算笔账：你的对象头到底吃了多少内存？

很多开发者知道“Java 对象头”，但很少去抠它到底占了多少空间。

在 64 位 HotSpot 上，不管你 new 出来的对象有没有字段，都有一个对象头。传统布局是这样的：

* **Mark Word**：8 字节，存锁状态、GC 分代年龄、identity hashcode 等运行时元数据。
* **Klass Pointer**：4 字节，指向类元数据的指针（前提是开了指针压缩，堆小于 32GB 时默认开启）。

加起来 12 字节，但 HotSpot 要求对象大小按 8 字节对齐，所以实际占 16 字节。

你 new 一个 `Object()`，什么都没存，光对象头就吃掉 16 字节。如果你有一个包含两个 int 字段的小对象，字段本身占 8 字节，加上对象头 16 字节，总共 24 字节——其中三分之二是对象头。

我之前用 JOL（Java Object Layout）跑过一个典型 Spring Boot 应用的堆转储，存活对象大概 300 多万个，平均对象大小在 48 字节左右。算下来对象头占总堆的比例在 **25% 到 30%** 之间。将近三分之一的堆内存，花在了对象的管理信息上，而不是你的业务数据上。

---

### JDK 27 怎么做的：把 12 字节压到 8 字节

JEP 534 的核心操作很直接：**把 Klass Pointer 塞进 Mark Word 里，整个对象头压缩到一个 64 位字。**

传统 64 位 Mark Word 的位分布大致是：低 2 位存锁状态，然后几位存 GC 年龄，31 位存 identity hashcode，剩下大量高位是空闲的。Lilliput 项目（这个特性的代号）的思路就是：既然高位闲着，为什么不用来存类指针？最终把 Klass Pointer 压缩到 22 位，嵌入 Mark Word 的空闲位中。

前提有两个：
1. 指针压缩必须开启（默认开启）
2. Metaspace 的基地址按 4MB 对齐（JDK 内部已经处理好了）

对象头从 12 字节变成 8 字节，每个对象省 4 字节。单看 4 字节好像不多，但中等规模的 Java 服务堆里往往有数百万甚至数千万个对象。

---

### 实测数据：锯齿状的内存节省

先说官方数据。SPECjbb2015 基准测试：堆内存减少 22%，CPU 时间减少 8%，GC 次数减少 15%。JDK 团队发行说明里给的保守估计是“堆大小减少约 20%”。

但这里有个很多人会忽略的细节：**不是每个对象都能省下这 4 字节。**

因为对象大小必须按 8 字节对齐。参考一组第三方基准测试的数据，测了五种微型类（0 到 4 个 int 字段），每种 1000 万个实例，用 MemoryMXBean 测量：

| 字段数 | 标准对象头 | 紧凑对象头 | 节省比例 |
| :--- | :--- | :--- | :--- |
| **0 个 int** | 16.00 B | 8.00 B | **-50%** |
| **1 个 int** | 16.01 B | 16.00 B | **0%** |
| **2 个 int** | 24.00 B | 16.00 B | **-33%** |
| **3 个 int** | 24.00 B | 24.00 B | **0%** |
| **4 个 int** | 32.00 B | 24.00 B | **-25%** |

这是一个锯齿状的分布。0 个字段的对象省了 50%，1 个 int 字段的对象一点没省，2 个 int 的省了 33%，3 个 int 的又没省。

**原因分析**：
标准对象头 12 字节，紧凑对象头 8 字节，省了 4 字节。但对象总大小要对齐到 8 字节的倍数：
- 若标准布局下对象总大小正好是 16 字节（例如对象头 12 字节 + 4 字节填充 = 16 字节），紧凑布局下变成 8 字节 + 0 字节填充 = 8 字节，省了整整 8 字节。
- 而当标准布局下对象是 12 字节头 + 4 字节字段 = 16 字节时，紧凑布局变成 8 字节头 + 4 字节字段 + 4 字节填充 = 16 字节，一分没省。

所以“堆内存减少 20%”这个数字，取决于应用里对象的大小分布。如果应用里大量是小对象（比如 DTO、配置对象、缓存条目），收益会接近官方数据。

作者自己的 Spring Boot 服务实测：堆内存从 2.1GB 降到了 1.7GB 左右，大约节省了 **19%**。

---

### 隐性收益：数据局部性才是真香

堆内存降了是好事，但在云环境下，更核心的收益在于**数据局部性（Data Locality）**的改善：

1. **CPU 缓存命中率提高**：对象头缩小后，堆上对象排布更紧凑，单位内存页里能放更多对象。CPU 读内存按缓存行（通常 64 字节）读取，对象变小意味着一个缓存行能装下更多对象，遍历时无需频繁从主存重新加载数据。
2. **TLB Miss 减少**：同样的工作集占用更少的物理内存页，TLB（地址转换缓存）miss 更少，CPU 等待内存的时间大幅缩短（对应 SPECjbb2015 中 8% 的 CPU 时间缩减）。
3. **GC 压力降低**：对象总大小变小导致 Young GC 触发频率降低，单次 YGC 需要扫描和复制的对象量也减少。对延迟敏感的服务而言，STW 暂停次数降低比单纯省内存更具价值。

### 踩坑记录：差点被 RSS 骗了

在 OpenJDK 邮件列表和实际升级中存在一个现象：部分 Spring Boot 应用从 JDK 25 升级到 JDK 27 EA 版本后，启动后的 **RSS（常驻内存集）反而有所上升**（例如不开 AOT 时从 149MB 升到 189MB 左右）。

> [!warning] 注意辨析 RSS 与堆内存
> - **根因**：该现象主要来自 JDK 27 的其他变更（例如 G1 成为全环境默认 GC 等），与紧凑对象头本身关系不大。
> - **认知**：**堆内存节省 ≠ 进程整体 RSS 下降**。JVM 进程的 RSS 还受 Code Cache、Metaspace、线程栈、GC 内部数据结构等影响（G1 在小内存容器中的自身开销高于 Serial GC）。
> - **建议**：重点观察堆使用量和 GC 行为指标，切勿仅凭单一 RSS 判断。
> - **工具兼容性**：JOL 需升级到与 JDK 27 匹配的版本，否则推算出的对象大小可能不准确。

### 适用场景评估

紧凑对象头并非所有场景都能获得显著收益：

| 场景 | 收益预期 | 说明 |
| :--- | :--- | :--- |
| **典型 Spring Boot 微服务** | **高（明显）** | 堆中存在数百万计的中小型对象（DTO、Bean、事件、HTTP 上下文等） |
| **领域对象普遍偏大** | 低 / 不明显 | 单个对象动辄数百或上千字节，对象头占比极低 |
| **存活对象数量较少** | 低 | 堆内仅数万或数十万对象，节省的绝对体积有限 |
| **已使用 ZGC / Shenandoah** | 边际递减 | 这类低延迟 GC 本身已有良好的内存管理和优化 |
| **GraalVM Native Image** | 机制不同 | Native Image 具有自有的内存布局优化路径 |

### 升级操作指南

#### 1. 确认特性生效

JDK 27 中紧凑对象头默认开启，无需额外添加参数。可通过以下命令确认：

```bash
java -XX:+PrintFlagsFinal -version 2>&1 | grep UseCompactObjectHeaders
```

预期输出：
```text
UseCompactObjectHeaders = true {default}
```

#### 2. 升级 Checklist

- [ ] 备份当前 JVM 参数与监控基线
- [ ] 在测试环境升级至 JDK 27（无需添加额外参数）
- [ ] 持续观察堆内存水位、GC 频率、P99 响应时间至少 24 小时
- [ ] 对比 RSS 与堆内存实际使用量，综合评估
- [ ] 如使用 JOL 等分析工具，升级至适配 JDK 27 的版本
- [ ] 若此前手动配置过 `-XX:+UseCompactObjectHeaders`，可直接移除

#### 3. 回退策略与注意事项

- **临时回退参数**：`-XX:-UseCompactObjectHeaders`（注：该参数已被标记为弃用，未来版本将彻底移除）。
- **历史 Bug 说明**：在 JDK 27 正式 GA 前的测试中曾有一例 C2 编译器断言失败，该问题已在正式 GA 版本前修复。
- **改动成本**：无需修改业务代码、无需重新调整参数、无需重新编译。

### 总结与感悟

作者从事 Java 开发十年（从 JDK 6 跨越至 JDK 27）。在 Java 演进史上，绝大多数性能提升通常需要代码重构、新 API 接入或繁琐的 GC 调优，而**紧凑对象头（JEP 534）**属于直接在 JVM 底层重构内存布局、对上层应用完全透明且默认开启的“零成本”优化。
