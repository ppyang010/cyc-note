## 核心结论

Subagent 不是免费的并行劳动力，而是**有成本的上下文隔离执行**。是否拆分，不看能安排多少“角色”，而看任务是否具备清晰的上下文边界，以及并行、降噪收益能否覆盖上下文重传、重复探索和结果合并成本。

复杂任务应先由主 Agent 串行建立共识，再把真正独立的部分交给 subagent 并行处理。最终判断、整合和验证仍由主 Agent 负责。

## 为什么多 Agent 可能更差

每增加一个 subagent，通常都会增加四类成本：

1. **上下文重传**：目标、背景、约束、相关文件、禁止事项、输出格式和验证方式都要重新传递。
2. **重复探索**：如果起点不明确，subagent 会重新搜索仓库，并可能误入旧版本或相似业务代码。
3. **结果合并**：不同 subagent 可能基于不同接口、类型或假设工作，产生文件冲突或更隐蔽的语义冲突。
4. **责任归因**：出错可能源于任务拆分、上下文缺失、错误假设、整合遗漏或测试不足，定位更困难。

因此，多窗口同时运行不等于真正并行。任务不独立、接口不清楚、结果不可验证时，只会形成“并行幻觉”。

## 适合拆 subagent 的任务

- 研究与代码搜索：查调用点、入口、依赖影响、实现差异。
- 只读 Review：基于 spec、diff 和测试结果识别风险。
- 专项安全检查：按明确 checklist 检查权限、敏感信息、危险依赖等。
- 独立模块实现：接口契约已确定，模块和文件边界清晰。
- 高噪声任务：大量日志、文件和候选点分析，适合隔离中间过程。
- 并行验证：分别执行前后端测试、lint、typecheck 或失败分析，且不争抢文件。

共同特征是：**边界清楚、低耦合、输出可独立验证、合并成本低**。

## 不适合拆 subagent 的任务

- 需求、范围或验收标准尚未明确。
- 状态流横跨多个组件、接口、hook 和测试，彼此高度耦合。
- 强依赖主会话中的历史讨论、用户否决项和隐性约束。
- 多个 subagent 可能修改同一批文件。
- 任务描述抽象且难以验证，例如“优化架构”“提升代码质量”。
- 单 Agent 已能清楚完成，拆分只是在模拟人类岗位。

## 判断公式

只有当下列收益明显大于成本时才拆分：

> 并行节省时间 + 隔离噪声 + 专项能力 + 边界清晰度  
> **大于**  
> 上下文重传 + 重复探索 + 结果合并

拆分前再检查三个必要条件：

1. 任务是否独立？
2. 接口是否清楚？
3. 结果是否可验证？

任一条件不满足，应先由主 Agent 串行澄清或执行。

## 正确工作流

1. **主 Agent 建立共识**：明确目标、验收标准、改动范围和关键上下文。
2. **按上下文边界拆分**：不要机械地按 planner、developer、tester 等岗位拆分。
3. **下发完整任务包**：包含目标、背景、输入材料、允许事项、禁止事项、输出格式和验证要求。
4. **要求结构化交付**：说明查看和修改的文件、所用假设、不确定点、验证结果及主 Agent 注意事项。
5. **主 Agent 统一整合**：识别冲突、核对假设、合并结论并决定下一步。
6. **用测试和 CI 验证**：不能把 subagent 的“已完成”当作最终证据。

## 可复用任务包模板

```text
任务：<边界明确的只读分析、独立实现或验证任务>

背景：
<完成任务所必需的上下文和已经确认的决策>

输入材料：
- <入口文件、diff、日志或接口契约>

需要回答或完成：
1. <具体事项>
2. <具体事项>

允许：
- <可读取、可修改或可执行的范围>

禁止：
- <不可修改的文件、不可扩大探索的范围>

输出格式：
- 相关文件和证据
- 结论或改动
- 假设与不确定点
- 验证命令及结果
- 风险和主 Agent 注意事项
```

## Skill、Subagent 与 Hook 的分工

- **Skill** 定义“怎么做”，可以由主 Agent 或 subagent 执行。
- **Subagent** 决定“在哪个隔离上下文中做”，适合降噪和独立执行。
- **Hook/CI** 负责强制门禁。密钥扫描、禁止删除测试等高风险规则必须程序化，不能只依赖 subagent 提醒。

## 实践路径

团队可以按风险逐步引入：

1. 单 Agent + 清晰任务 + 测试门禁。
2. 引入代码搜索、Review、安全检查等只读 subagent。
3. 引入不同模块的并行探索，但暂不并行写代码。
4. 在契约、文件边界和测试都清晰后，尝试独立模块并行实现。
5. 最后再建设完整的 Agent Team 协作流程。

## 一句话原则

多 Agent 协作追求的不是 Agent 数量，而是**合理的任务边界、最低必要的上下文传递，以及可验证的交付闭环**。
