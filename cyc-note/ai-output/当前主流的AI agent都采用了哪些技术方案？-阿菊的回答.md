# 当前主流的AI agent都采用了哪些技术方案？

> [!info] 来源信息
> - 作者：阿菊
> - 来源：[知乎回答](https://www.zhihu.com/question/2047817495432655100/answer/2076710796164450109)
> - 抓取日期：2026-08-28
> - 说明：本文是对原回答的结构化整理，保留作者的主要观点。原回答中的项目、架构数字、行业判断和外部链接，未在本笔记中逐项独立核验。

## 一句话理解

这篇回答的核心判断是：**通用 Agent 的竞争重点，已经从提示词工程转向全栈系统工程。** 一个能在开放环境中稳定工作的 Agent，不只是“模型 + 工具调用”，还需要推理规划、代码执行或图形界面交互、上下文与状态管理、容错恢复、评测和安全护栏共同形成闭环。

可以把它概括为：

> **强推理模型 + 受控执行环境 + 确定性流程边界 + 动态反馈回路 + 可量化评测**

## 一、底层推理与规划：从外挂逻辑到内置思考

### 1. 长思考能力的混合推理模型

回答认为，通用 Agent 的核心底座正在转向具备测试时计算能力的推理模型。模型在真正执行动作前，会进行更长的思考、自我反思、假设检验和路径剪枝，从而把一部分过去依赖外部代码实现的重试和规划逻辑，消化到模型自身的推理过程中。

这带来两个工程含义：

- 基座模型的推理和代码能力，往往比复杂提示词技巧更重要。
- 外部编排不应重复实现模型已经能够稳定完成的推理工作，但仍要负责权限、边界和失败恢复。

### 2. 代码即动作

回答认为，开放任务中的主流 Agent 越来越倾向于让模型在沙箱中编写和执行 Python 或 Bash，而不是为每个动作都输出严格的 JSON 工具调用。

代码驱动方式的优势：

- 可以自然表达循环、条件判断、批处理和数据清洗。
- 调 API、处理文件、运行命令和分析结果可以放在同一个执行环境中完成。
- 解释器会把标准输出、错误堆栈和生成文件直接反馈给模型，便于自我修正。
- 动作表达能力比固定的工具 Schema 更灵活。

但这也把安全重点推向沙箱隔离、文件权限、网络权限、依赖安装、资源限制和检查点恢复。

## 二、当前通用 Agent 的三条主流技术路线

### 路线一：基于安全沙箱的代码驱动系统

这是自动化任务、数据科学和自动化软件研发中较成熟的一条路线。基本闭环是：

1. 模型接收高层目标并拆分阶段性里程碑。
2. 模型在独立容器或沙箱中编写脚本、执行命令、安装依赖并操作文件。
3. 系统捕获标准输出、标准错误和生成文件，作为下一轮上下文。
4. 模型检查结果；成功则推进，失败则根据错误堆栈修正后重试。

主要技术壁垒不只是模型，而是沙箱隔离、状态恢复速度、长上下文管理，以及在环境被破坏时快速回滚到检查点的能力。

### 路线二：基于多模态视觉的操作系统与网页控制

这条路线面向浏览器和桌面 GUI，目标是让 Agent 像人一样观察屏幕、移动鼠标和敲击键盘。

主要技术点包括：

- **视觉定位与坐标映射**：根据截图识别按钮、输入框和目标区域，并输出点击或操作坐标。
- **图文双轨感知**：同时利用截图和清洗后的无障碍树或页面语义信息，兼顾通用性、文本准确性和交互速度。
- **人类接管**：遇到验证码、多因素认证和复杂风控时暂停，让人完成认证后恢复任务。

纯视觉方案更通用，但推理延迟和误点风险更高；纯 DOM 方案更精确，却难以覆盖 Canvas、复杂动态页面和桌面应用，因此实际系统往往采用混合感知。

### 路线三：基于确定性状态图的多 Agent 协作

回答反对把多个模型放进自由群聊，就认为它们能自动协作解决长任务。完全去中心化的对话容易出现误差累积、语义漂移、死循环和资源浪费。

更适合生产环境的方式是：

- **中央调度器**：维护全局状态，决定任务当前所在节点并分发工作。
- **专业化工作节点**：每个节点拥有较窄的上下文和明确的工具集，例如检索、结构化提取、审查或执行。
- **显式契约传输**：节点之间传递强类型结构化数据，使用 Schema 校验中间结果；校验失败时局部重试，不让脏数据污染下游。

可以记成一句话：**骨架用确定性代码控制，血肉让模型发挥。**

## 三、通用 Agent 绕不开的四个核心模块

### 1. 上下文与状态管理

长任务不能把全部历史记录原样塞回模型，需要进行上下文工程：

- 主动截断和提炼超长日志，只保留报错、关键返回值及必要上下文。
- 把全局变量、已完成子目标、已生成文件和环境状态外部化持久化。
- 通过滑动窗口、结构化观察值和任务摘要，降低注意力分散与延迟。

### 2. 工具与沙箱环境

工具层要解决模型如何安全地影响外部世界，包括：

- Bash/Python 代码执行。
- 文件系统、数据库和网络访问。
- 浏览器与桌面 GUI 驱动。
- 容器隔离、权限控制、资源限制和依赖管理。

工具描述和参数设计要清晰，工具数量并不是越多越好。大量能力重叠、描述模糊的 API 反而会增加模型选择错误的概率。

### 3. 评测与反馈机制

不能只靠人工查看日志判断 Agent 是否变强。应在隔离环境中录制一批包含标准起点和预期终点的任务，迭代时比较：

- 任务完成率。
- 最终文件、数据库记录或接口调用是否正确。
- 平均执行时长和 Token 消耗。
- 错误类型、重试次数和轨迹质量。

还需要语义输出校验、轨迹回放、确定性 Mock 基准和安全护栏，确保模型升级或提示词修改不会悄悄破坏系统。

### 4. 核心推理与规划引擎

推理引擎负责理解目标、拆解任务、选择动作、解释反馈并在必要时调整计划。外层系统则负责把模型能力放在受控的流程、工具权限和资源预算内。

## 四、持久化执行与动态知识获取

### 持久化执行与容错

长时间运行的 Agent 会遇到网络抖动、模型超时、第三方 API 限流和局部执行失败。回答建议借鉴持久化工作流引擎的设计：

- 每个动作和环境返回都记录为不可变事件日志。
- 在成功节点建立检查点。
- 任务崩溃后从最后一个成功事件恢复，而不是从头执行。
- 关闭顺序与启动顺序相反，避免任务继续写入已经停止的资源。

### 混合检索与动态知识获取

通用 Agent 面对未知库、私有 API 或生僻事实时，需要实时建立临时知识上下文。回答强调两类能力的组合：

- 主动抓取并解析官方文档，快速构建分块索引。
- 对代码和精准配置优先使用 rg 等文本搜索工具，而不是完全依赖向量相似度。

## 五、作者强调的三个工程判断

1. **不要用复杂提示词弥补基座模型能力不足。** 如果模型的推理和代码能力不够，继续叠加自反思、角色扮演和提示词框架，可能只会增加延迟和成本。
2. **不要在开放任务中迷信纯自主编排。** 生产系统更适合确定性骨架加受约束的模型决策，而不是把控制流完全交给多个 Agent 自由发挥。
3. **工具质量比工具数量重要。** 清晰、稳定、边界明确的工具，比大量重叠且描述不清的 API 更容易让系统可靠运行。

## 六、适合落地时记住的架构原则

- 先选对推理模型，再设计外部编排，不要本末倒置。
- 把模型的自由度限制在可验证的节点和动作空间内。
- 对代码执行、文件写入、网络访问和 GUI 操作建立最小权限。
- 把状态、事件、检查点和轨迹记录在模型上下文之外。
- 用可重复的任务集做回归评测，并同时关注成功率、成本和耗时。
- 遇到验证码、支付、发送消息等高风险动作，保留人工确认或接管通道。

## 我的理解

这篇回答最值得记住的不是某个具体框架，而是一个工程取舍：**让模型负责不确定的语义判断，让代码负责确定的流程和安全边界。**

通用 Agent 的能力上限取决于模型，但能否稳定进入生产环境，更多取决于沙箱、状态、容错、评测、权限和反馈闭环。
