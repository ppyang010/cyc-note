# 新手小白求解答：到底什么是Agent?

> [!info] 来源信息
> - 作者：DHPP（按用户提供的标题记录）
> - 来源：[知乎回答](https://www.zhihu.com/question/2060386189761422257/answer/2076247857238221750)
> - 抓取日期：2026-08-27
> - 说明：本文是对原回答的结构化整理，知乎原文中的配图未下载。原文涉及的框架、协议、行业数据和时间性判断，以原文引用为准，未在本笔记中逐项独立核验。

## 一句话理解

按这篇回答的主线，Agent 可以理解为：**以 LLM 为核心，在目标驱动的循环中使用工具、读取环境反馈、不断决定下一步行动，直到完成任务或触发退出条件的系统。**

也可以记成：

> Agent = 大模型的大脑 + 外部工具的手脚 + 记忆/状态 + 规划与反馈循环 + 工程护栏

它和普通聊天机器人的关键区别，不是“会不会聊天”，而是能否在较少的逐步提示下，围绕目标连续完成多步任务。

## 从 Chat Bot 到 Agent

普通 LLM 更像一个“有知识、会表达的顾问”：

- **知识可能被冻结**：训练数据有截止时间，不天然知道最新事实。
- **只能输出文字**：可以告诉你如何发邮件、改代码、查天气，但本身不会点击发送、修改文件或调用接口。
- **缺少持续状态**：一次调用结束后，不会自动保留任务中间结果；跨任务记忆需要由外部系统提供。
- **不会天然执行复杂流程**：面对“先调研、再分析、再写报告”这类任务，单次调用通常只是一次性生成文字。

给模型接入搜索、文档、数据库、代码执行器、邮件 API、文件系统或其他应用后，它才有了与外部世界交互的能力。再加上任务状态、工具调用循环和结果检查，就形成了工程意义上的 Agent。

## Agent 的核心闭环

一个典型 Agent 的运行过程可以抽象为：

```text
用户目标
  ↓
感知当前环境与任务状态
  ↓
规划或判断下一步
  ↓
调用工具并执行动作
  ↓
读取工具结果
  ↓
判断是否完成、是否重试或是否调整计划
  ↺ 未完成则继续循环
```

常见的 ReAct 表达是：

```text
Thought（思考）→ Action（行动）→ Observation（观察）→ Thought（再次思考）
```

循环需要有明确的停止条件，例如任务完成、达到最大轮数、工具报错无法恢复，或需要人工审批。

## 三个关键能力

### 1. 工具调用：从“会说”到“能做”

工具调用是 Agent 产生行动能力的关键。工具可以是：

- 搜索引擎和网页读取器
- 数据库、文件系统和代码执行器
- 天气、日历、邮件等业务 API
- 浏览器、办公软件或其他外部应用

需要特别区分“模型做决定”和“程序执行动作”：

1. 开发者把工具名称、能力描述和参数 Schema 提供给模型。
2. 模型根据当前任务输出结构化的工具调用请求，例如工具名和 JSON 参数。
3. 外层的 Harness（调度/编排程序）解析请求，真正执行工具。
4. Harness 把执行结果放回上下文，模型再决定下一步。

因此，模型并没有直接执行函数；它输出的是“应该做什么”的结构化预测，真正控制权限和执行副作用的是应用层。

例如，用户要求“查北京天气，然后发邮件给老板”：模型可以先选择 `get_weather(city="北京")`，拿到天气结果后，再生成 `send_email(...)` 的调用请求；天气查询和邮件发送都由外层程序实际完成。

### 2. 记忆与状态：从“做一步忘一步”到保持连贯

Agent 通常需要区分两种记忆：

- **短期记忆**：当前任务的对话、中间结果、工具返回值、已完成步骤和错误信息，通常存在运行状态或上下文中。
- **长期记忆**：跨任务保存的用户偏好、历史操作、知识资料或业务记录，通常由数据库、向量库或其他存储系统承载，并在需要时检索。

记忆不是 LLM 自动拥有的永久能力，而是 Agent 系统通过上下文管理和外部存储提供的能力。

### 3. 多步推理与自我纠错：遇到问题能调整

Agent 与简单自动化脚本的差异，还体现在执行过程中的反馈处理：

- 搜索结果无效时，换关键词或换数据源。
- API 报错时，分析错误信息并修正参数。
- 任务结果不符合要求时，回到前一步重新执行。
- 交付前进行自我检查，必要时让另一个 Agent 或人工进行复核。

这使 Agent 更适合处理不确定、需要多步探索的任务，但也会带来更多 Token、时间、成本和不可预测性。

## Workflow 和 Agent Loop 的区别

“用了 LangGraph”并不自动意味着系统就是高度自主的 Agent。关键要看：**下一步由谁决定，是代码还是模型。**

### 固定流程编排

流程图中的节点、边和分支都由开发者预先确定：

```text
开始 → 节点 A → 节点 B → 节点 C → 结束
```

模型可能只负责分类、抽取或生成某个节点的内容，整体路线由代码控制。这更接近 Workflow 或自动化脚本，优点是稳定、可预测、容易测试。

### Agent Loop

Agent Loop 只规定可用的工具、状态、循环边界和安全规则；每轮由模型根据当前结果判断：

- 是否需要调用工具；
- 调用哪个工具；
- 参数如何填写；
- 工具结果是否可信；
- 是否继续循环、重试、改变计划或结束。

LangGraph 的普通边可以是确定性路径，条件边则可以根据状态路由。如果条件边的返回值由 LLM 输出决定，那么具体走向就是模型在约束空间内做出的选择。

所以可以把 LangGraph 理解为“地图”或“操场边界”，而不是必然的铁轨：拓扑结构和护栏由工程师设计，具体决策点可以交给模型。

## 自主性不是开关，而是一根滑杆

不同资料对 Agent 的定义并不完全一致：

- 有的定义强调 LLM 是否控制步骤和工具使用。
- 有的定义强调系统能否代表用户独立完成任务。
- 有的定义强调观察、推理、行动的循环。
- 有的定义直接把 Agent 归纳为“用 LLM 决定应用控制流的系统”。

因此，与其争论一个系统“是不是 Agent”，不如判断它“有多 Agentic”：

```text
单次 LLM 调用
  → 提示词链
  → 固定分支工作流
  → 模型选择工具的循环
  → 模型动态规划与反思
  → 编排者协调多个子 Agent
  → 多 Agent 自主协作
```

自主性越高，灵活性通常越强，但可预测性、成本控制、测试和责任归因也会变得更困难。现实系统往往处在中间状态：外层用确定性流程和权限控制兜底，内层在部分节点把选择权交给模型。

## LLM 的“决定”到底是什么

从机制上说，LLM 并没有像人一样直接调用函数。它做的事情仍然是根据上下文预测下一个 Token，只是经过训练后，能够更稳定地输出工具调用所需的结构化文本。

这两句话可以同时成立：

- **工程视角**：如果外层代码没有把下一步写死，而是由模型选择工具、参数和是否继续，那么这是模型在受限空间内做出的决策。
- **机制视角**：这个决策的底层仍然是概率性的 Token 生成，不意味着模型具有人类式意图或意识。

理解这条边界，有助于正确设计安全机制：模型负责提出行动建议，应用层负责校验、授权、执行和记录。

## MCP 与 A2A 的定位

原回答把 Agent 生态中的两个协议做了对比：

| 协议 | 解决的问题 | 可以怎样理解 |
| --- | --- | --- |
| MCP（Model Context Protocol） | Agent 如何发现和调用外部工具/资源 | Agent 与工具之间的通用接口，类似 USB-C |
| A2A（Agent2Agent） | 不同 Agent 如何发现能力、分配任务和传递结果 | Agent 与 Agent 之间的协作协议 |

简化理解：**MCP 管“伸手拿工具”，A2A 管“和其他 Agent 协作”。**

原文还提到 Host、Client、Server 等 MCP 架构角色，以及 A2A 的 Agent Card。相关协议版本、捐赠时间、生态规模等属于会随时间变化的信息，使用时应以对应官方资料为准。

## 什么时候用 Workflow，什么时候用 Agent

这篇回答给出的核心取舍是：

> Workflow 用可预测性换取较少的自主性；Agent 用自主性换取较少的可预测性。

可以用下面的清单判断：

### 更适合 Workflow 的情况

- 完整决策树可以提前画出来。
- 每一步规则明确、重复性高。
- 结果需要稳定、可审计、低成本。
- 错误代价高，且不值得让模型自由探索。

### 更适合 Agent 的情况

- 任务目标明确，但完成路径无法提前穷举。
- 需要搜索、试错、动态选择工具或根据反馈调整计划。
- 环境和输入变化较大，固定分支很快会失效。

### 高风险任务的护栏

- 使用最小必要权限，优先只读工具。
- 对发邮件、写数据库、删除文件、支付等副作用动作设置人工审批。
- 限制循环轮数、重试次数、Token 和预算。
- 对工具参数做 Schema 校验和业务授权校验。
- 记录每一轮的输入、模型选择、工具调用、返回结果和最终状态。
- 让结果可回滚，并设置超时、熔断和失败退出条件。

## 如何判断一个系统是否真的“像 Agent”

可以连续问这几个问题：

1. 它是否围绕一个目标执行，而不是只做一次文本生成？
2. 下一步路线是代码完全写死，还是模型可以在候选空间内选择？
3. 它是否能够调用外部工具并接收真实结果？
4. 工具结果是否会影响后续决策？
5. 它是否有任务状态、停止条件和失败处理？
6. 模型输出的工具调用是否经过应用层校验和授权？
7. 每一步是否可观察、可追踪、可复盘？

如果每一步都是固定的 `if-else`，LLM 只负责填模板中的几个字段，那么它更准确地说是“带 LLM 的 Workflow”或自动化脚本。只要模型能根据当前状态重新评估并选择下一步，系统才具有更明显的 Agent 特征。

## 新手记忆版

可以用五个比喻快速记忆：

- **LLM**：大脑，负责理解、推理和提出下一步。
- **工具**：手和脚，负责查询、写入、执行和操作外部系统。
- **记忆/状态**：笔记本，保存当前任务和跨任务信息。
- **循环**：工作方法，做一步、看结果、再决定下一步。
- **Harness/编排层**：护栏和指挥台，负责权限、流程边界、执行、重试、审批和日志。

最终要记住的不是“Agent 会自己思考”这句拟人化描述，而是：**编排负责定义边界和骨架，自主性发生在具体决策点；真正可用的 Agent，是在可控边界内可靠地把目标完成。**
