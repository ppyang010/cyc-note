## 大堆下的收集器选择

| 收集器 | 机制 | 容量规划关注点 |
| --- | --- | --- |
| G1 | 将堆划分为 Region，按预测的回收开销和停顿目标选择收集集合。 | 关注分配速率、对象存活量和用于对象转移的空闲 Region。分配与回收失衡时，可能出现转移失败和 Full GC。 |
| ZGC | 通过染色指针和屏障支持并发标记、重定位等工作，缩短 GC 停顿。 | 需要给并发回收预留 CPU 和堆空间。判断低延迟能否达标时，也要观察分配停滞和应用请求延迟。 |

原文提到的 64 GiB 可作为讨论 G1 大堆运行的量级。G1 的适用堆大小仍需按 JDK 版本、硬件和负载来判断。Full GC 自 JDK 10 起已可并行执行。Oracle 的 JDK 25 文档将 ZGC 的适用堆大小描述为数百 MB 到 16 TB。[OpenJDK JEP 307](https://openjdk.org/jeps/307) · [Oracle 收集器选型指南](https://docs.oracle.com/en/java/javase/25/gctuning/available-collectors.html)

## 容量预算与参数

- **预留进程与系统内存。** 堆预算以进程可用的物理或容器内存上限为起点，留出 Metaspace、线程栈、直接缓冲区、其他本地内存和系统开销。原帖给出的 50%–70% 是经验区间，具体比例由实测峰值和余量决定。
- **根据资源条件评估配置。** 原帖建议将 `-Xms` 和 `-Xmx` 设为相同值来减少扩缩容，并讨论了 Swap、大页和 GC 线程数。这些设置改变常驻内存、系统行为或 CPU 竞争，比较时应在同一负载下查看 GC 日志、吞吐和尾延迟。
- **给直接缓冲区单独做预算。** 直接缓冲区的数据位于堆外，对象本身仍受 Java 生命周期管理。`-XX:MaxDirectMemorySize` 用于限制 NIO 直接缓冲区的分配。其他本地分配和进程总内存也要计入容量，仍需管理缓冲区生命周期。

## 分代 ZGC 的版本差异

| JDK 版本 | 启用方式 |
| --- | --- |
| 15–20 | `-XX:+UseZGC` 使用非分代 ZGC。JDK 15 将 ZGC 转为生产可用功能。 |
| 21–22 | `-XX:+UseZGC -XX:+ZGenerational` 选择分代 ZGC。 |
| 23 | `-XX:+UseZGC` 默认使用分代模式，`ZGenerational` 参数已弃用。 |
| 24 起 | `-XX:+UseZGC` 使用分代模式。非分代模式已移除，旧参数应从配置中移除。 |

### 超大内存 JVM 的技术底座：从 G1 到 ZGC 的演进

传统分代模型在面对超大堆内存时，其局限性日益凸显。当堆内存达到数十 GB 甚至 TB 级别时，传统的垃圾回收器（如 Parallel GC 或早期的 CMS）在进行全堆扫描和整理时，停顿时间会随着堆大小线性增长，这是低延迟系统无法容忍的。  

#### 1. G1 的区域化与瓶颈

G1（Garbage-First）收集器是首个在 HotSpot JVM 中实现区域化（Region-Based）内存管理的垃圾回收器。它将堆划分为多个等大小的 Region，通过预测模型来控制停顿时间。然而，G1 能管理的最大堆内存通常在 64G 左右（受限于 Region 数量和大小）。在高并发场景下，如果业务线程分配内存的速度超过了 G1 回收的速度，极易触发“Evacuation Failure”（转移失败），导致 G1 退化为单线程的 SerialOld 收集器，此时系统会挂起所有业务线程去清理几十 G 的内存，直接导致系统假死。  

#### 2. ZGC 的染色指针与 TB 级支持

为了彻底解决超大内存的延迟问题，ZGC（Z Garbage Collector）应运而生。ZGC 的核心技术底座在于 **染色指针（Colored Pointers）**和**读屏障（Load Barriers）** 。
- **染色指针** ：ZGC 利用 64 位系统的特性，将对象的标记状态（如 Marked0、Marked1、Remapped）直接存储在指针的高位中，而不是对象头里。
- **并发重定位** ：借助染色指针和多重映射技术，ZGC 可以在不暂停应用线程的情况下，在后台并发地移动对象。当业务线程访问正在被移动的对象时，读屏障会拦截访问并修正指针。
  
通过这种机制，ZGC 成功将 GC 停顿时间控制在 10 毫秒以内，且停顿时间不随堆大小线性增长，理论上支持高达 16TB 的堆内存，为超大内存 JVM 提供了坚实的技术底座。

### 二、 超大内存 JVM 的容量规划与参数配置

在明确了技术底座后，容量规划需要结合物理硬件、操作系统以及业务特性进行综合考量。  

#### 1. 堆内存与物理内存的边界规划

- **物理内存预留** ：JVM 堆内存（-Xmx）绝不能设置为等于或接近服务器的物理总内存。必须为操作系统、元空间（Metaspace）、线程栈、堆外内存（DirectByteBuffer）以及其他系统进程预留充足的空间。通常建议堆内存占物理总内存的 50%-70%。
- **禁用 Swap** ：对于大内存应用，必须禁用操作系统的 Swap 分区（swapoff -a）。一旦发生内存交换，GC 时的磁盘 I/O 剧烈波动会严重拖垮系统性能。

#### 2. 核心 JVM 参数配置策略

- **固定堆大小** ：将初始堆（-Xms）和最大堆（-Xmx）设置为相同值，避免运行时动态扩缩容带来的性能开销。
- **启用大页（Huge Pages）** ：在 Linux 系统中，启用大页可以显著减少 TLB（Translation Lookaside Buffer）的缺失率，提升大内存的访问效率。-XX:+UseLargePages -XX:LargePageSizeInBytes=2m
- **GC 线程与停顿控制** ：  
	- 若使用 G1，需根据 CPU 核心数合理设置并行线程数（-XX:ParallelGCThreads）和并发线程数（-XX:ConcGCThreads），通常并发线程数为并行线程数的 1/4。
	- 若使用 ZGC（Java 15+ 生产就绪），可直接通过 -XX:+UseZGC 启用，并配合 -XX:+ZGenerational（分代 ZGC）进一步提升吞吐量。

#### 3. 堆外内存与架构降维

对于海量缓存场景，最高级的容量规划往往不是在 JVM 堆内死磕。如果将几千万个对象硬塞进堆内存，任何 GC 都会面临巨大压力。架构上应采用“降维打击”策略：通过 DirectByteBuffer 将海量数据写入堆外内存（操作系统内存），彻底绕开 JVM 的垃圾回收机制，堆内仅保留少量的业务流转对象。同时，需通过 -XX:MaxDirectMemorySize 严格限制堆外内存上限，防止内存泄漏。  
  
超大内存 JVM 的架构进阶，本质上是一场在“吞吐量”与“延迟”之间的博弈。从 G1 的区域化到 ZGC 的染色指针，技术底座不断突破物理限制；而科学的容量规划，则要求我们跳出单一的 JVM 参数调优，将视角拉升到操作系统内存管理、堆外内存利用以及整体系统架构的层面。只有将底层原理与业务场景深度结合，才能真正驾驭超大内存，构建出高可用、低延迟的核心系统。
