# 第 1 讲：Task / Todo / Plan——未雨绸缪，有备无患

> **未雨绸缪，有备无患。**

第 0 讲里，我们让 Coding Agent 走进了工程现场。

但进入后厨，不等于会做饭。

用户说：

`帮我把这个项目修好。`

如果 Agent 立刻搜索、修改，它很容易像没有看菜单就开火的厨师：动作很多，却不知道最后要交付什么，也不知道做到什么程度才算完成。

所以，在给 Agent 更多工具之前，先要给它一本任务本。

这本任务本只解决三个问题：

```
Task：最终要完成什么？
Todo：这件事要拆成哪些小步骤？
Plan：根据当前状态，现在先做哪一步？
```

![Image 1](https://pic1.zhimg.com/v2-6e8f678adb97f7e82e6f463d8ec0bfac_1440w.jpg)

图 1：Task 像菜单卡，Todo 像备菜清单，Plan 决定当前下一步；执行结果还要写回任务本。

* * *

### 一、Task：先把“今天做什么”说清楚

“做顿饭”不是一张完整菜单，“修一下项目”也不是一个完整任务。

一个可执行的 Task，至少要说明三件事：

```
Goal：最终想得到什么；
Done when：出现哪些证据以后，才能算完成；
Constraints：哪些事情不能做。
```

![Image 2](https://pic4.zhimg.com/v2-d62642c0bc2b20278bf1be1e007773df_1440w.jpg)

图 2：Task 像菜单卡。先确定要做什么，再讨论怎样动手。

本系列继续使用 `enhanced_project` 作为贯穿案例。它的初始测试结果是：

`4 failed, 6 passed`

四个问题分别是：

```
add() 把加法写成了减法；
mean() 没有处理空列表；
median() 的偶数情况计算错误；
format_percentage() 在 total=0 时除零。
```

如果只是说“把项目修好”，Agent 可能只改其中一个问题，也可能改完以后不再测试。

更完整的 Task 应该写成：

```
Goal：
修复四个故障，让 10 个测试全部通过。

Done when：
1. 能复现 4 failed, 6 passed；
2. 找到四个真实根因；
3. 只修改必要代码；
4. 全部测试重新通过；
5. 没有无关改动；
6. 输出简短修复说明。

Constraints：
不删除测试，不降低测试要求，不做无关重构。
```

这里最重要的是 `Done when`。

它把“我感觉修好了”变成“我能证明修好了”。

* * *

### 二、Todo：把一桌菜拆成可以操作的工序

菜单确定以后，厨师不会把“完成晚饭”当成一个动作。

他会拆成：

```
看食材；
洗菜；
切菜；
备料；
下锅；
调味；
装盘。
```

Todo 的作用也是一样：把一个大任务拆成一组能执行、能检查的小步骤。

![Image 3](https://pica.zhimg.com/v2-97895e057db739b9657bc3479d459350_1440w.jpg)

图 3：Todo 像备菜清单。拆开以后，Agent 才能一项一项推进。

修复 `enhanced_project`，可以拆成：

```
1. 查看项目结构；
2. 阅读运行说明；
3. 运行测试，复现失败；
4. 阅读失败测试和相关源码；
5. 形成最小修改方案；
6. 修改代码；
7. 重新运行全部测试；
8. 检查改动并写报告。
```

Todo 不能只是一张静态清单，还要记录状态：

```
todo：还没开始；
doing：正在处理；
done：已经完成；
blocked：暂时无法继续。
```

同时，每做完一步都要留下 Observation，也就是“这一步实际看到了什么”。

例如：

```
运行测试：done
Observation：
初始结果为 4 failed, 6 passed，
失败集中在 add、mean、median 和 format_percentage。
```

这就像厨师在清单旁边写下：

```
汤已经开始炖；
家里没有香菜；
客人不能吃辣。
```

这些记录会直接影响下一步。

* * *

### 三、Plan：不是写长计划，而是决定当前下一步

Plan 经常被误解成一份很长的计划书。

但真实工程会不断出现新信息。

运行测试前，Agent 不知道问题具体在哪里；读完代码以后，它可能发现原来的判断是错的；修改完成以后，还要根据测试结果决定是否继续。

所以，Plan 更适合被理解为：

> **根据当前任务状态，选择现在最合理的一步。**

![Image 4](https://pica.zhimg.com/v2-97895e057db739b9657bc3479d459350_1440w.jpg)

图 4：Plan 像当前灶台安排。先把眼前最合理的一步做好，再继续往下走。

例如：

```
还没看目录，不急着运行未知命令；
还没复现失败，不急着改代码；
还没重新测试，不急着写“任务完成”。
```

这不是形式主义，而是工程顺序。

后厨里也是一样：食材没洗，不能直接下锅；汤要炖很久，就应该先开火；发现缺少关键调料，原计划还要调整。

* * *

### 四、Task、Todo、Plan 到底是什么关系？

| 概念 | 后厨对应物 | 回答的问题 |
| --- | --- | --- |
| Task | 菜单卡 | 最终要交付什么？ |
| Todo | 备菜清单 | 要做哪些小步骤？ |
| Plan | 当前工序 | 现在先做哪一步？ |

完整关系是：

```
用户需求
  ↓
Task：明确目标、完成标准和边界
  ↓
Todo：拆成步骤并记录状态
  ↓
Plan：选择当前下一步
  ↓
Agent Loop：执行、观察、更新、继续
```

Task 决定方向，Todo 保存过程，Plan 推动当前行动。

### 五、代码只需要帮助理解

第 1 讲不需要实现一个完整 Agent。代码只要能说明：

```
Todo 有完成状态；
系统能从当前状态中找出下一步。
```

最小示意：

```
todos = [
    {"name": "查看项目结构", "done": True},
    {"name": "运行测试", "done": False},
    {"name": "修改代码", "done": False},
]

def next_todo(todos):
    for item in todos:
        if not item["done"]:
            return item["name"]

print(next_todo(todos))
```

输出：

`运行测试`

这段代码并不完整，但已经表达了本讲最重要的思想：

> Agent 不是凭感觉乱走，而是根据任务状态选择下一步。

真正的工具调用、文件读写和循环执行，会在后面的 Agent Loop 与 Tools 中继续补上。

### 六、从 L1 到 L2：开始接住一项工作

```
L0 聊天顾问：能解释问题；
L1 代码副驾驶：能围绕局部代码给建议；
L2 项目助手：能接任务、拆步骤、维护状态；
L3 任务执行者：能调用工具并循环推进；
L4 工程队友：能处理长任务并接受 Review；
L5 AI 工作者系统：能被组织、审计和协同。
```

第 1 讲完成的是 **L1 → L2**。

Agent 还没有真正自动完成任务，但它已经拥有：

```
目标；
完成标准；
约束；
步骤；
状态；
观察记录；
当前下一步。
```

它不再只是站在厨房旁边说“我会做”，而是开始接住��张订单。

* * *

### 本讲小结

```
Task：先说明要完成什么；
Todo：把任务拆成小步骤；
Plan：根据当前状态选择下一步；
Observation：把执行结果写回任务本。
```

没有这套结构，Agent 只是被放进项目。

有了它，Agent 才真正开始工作。
