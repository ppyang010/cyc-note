# 第 10 讲：Subagent / Multi-agent——集思广益，群策群力

> **集思广益，群策群力。**
> 
> 出处说明：“集思广益”取意于诸葛亮“夫参署者，集众思，广忠益也”的表达，相关文字见[《三国志》](https://zhida.zhihu.com/search?content_id=281283924&content_type=Article&match_order=1&q=%E3%80%8A%E4%B8%89%E5%9B%BD%E5%BF%97%E3%80%8B&zhida_source=entity)所载材料；“群策群力”用于概括多方共同谋划、共同出力的协作精神。本讲将两者合并为多智能体协作的题眼。

第 9 讲讲的是：

```
把任务交给远程执行点；
主控下放任务并回收结果。
```

第 10 讲再向前一步。

它不只关心“谁去做”，而是关心：

```
一个复杂问题，能不能让不同角色分别观察、思考和判断？
这些不同意见，怎样交换？
最后由谁形成一致、完整的结果？
```

这就是 Subagent / Multi-agent。

![Image 1](https://pic4.zhimg.com/v2-fa953d52898647cad12146f632f9ccab_1440w.jpg)

图 1：Subagent 不是多个一模一样的 Agent，而是多个职责清晰的专业角色。

* * *

Subagent 可以理解成主 Agent 创建的专业助手。

它们通常有明确分工：

```
检索角色：查资料、找证据；
规划角色：拆任务、排步骤；
执行角色：运行工具、完成操作；
评估角色：检查结果、发现风险。
```

![Image 2](https://pic4.zhimg.com/v2-d6446241face42187ba775ce6a6f31d7_1440w.jpg)

封面：多个智能体分别承担数据、检索、规划、执行与评估，再由统一出口整合结果。

继续用修 Bug 案例：

```
测试分析子智能体：
读取 pytest 输出，归纳失败类型。

代码定位子智能体：
阅读相关源码，分析真实根因。

修复子智能体：
提出最小修改方案。

Review 子智能体：
重新检查测试、diff 和完成标准。
```

每个角色只处理自己擅长的一段，减少一个 Agent 同时兼顾所有事情时产生的混乱。

* * *

## 二、Multi-agent：不是分完工就各做各的

如果多个 Agent 只是分别输出自己的答案，却没有交换信息，这还不算高质量协作。

Multi-agent 更重要的是：

```
分头观察；
交换观点；
相互质疑；
整合证据；
形成共识。
```

![Image 3](https://pic2.zhimg.com/v2-9842c96fc7e8fa62255f4a5f30707c93_1440w.jpg)

图 2：多智能体的价值，不只是并行工作，还包括不同视角之间的相互启发和校验。

例如：

```
检索角色说：问题可能来自输入数据；
代码角色说：实现里缺少空列表判断；
测试角色补充：失败只出现在边界条件；
评估角色确认：最小修复应修改 mean()，而不是修改测试。
```

经过交换以后，结论比任何一个角色单独判断更可靠。

* * *

## 三、群策群力，也必须有统一收口

多 Agent 最常见的问题，不是没有答案，而是答案太多：

```
观点互相冲突；
重复分析同一问题；
输出格式不一致；
没人对最终结果负责。
```

所以[多智能体系统](https://zhida.zhihu.com/search?content_id=281283924&content_type=Article&match_order=1&q=%E5%A4%9A%E6%99%BA%E8%83%BD%E4%BD%93%E7%B3%BB%E7%BB%9F&zhida_source=entity)必须有一个明确的汇总角色：

```
去重；
核对矛盾；
判断证据强弱；
形成统一方案；
对外输出最终结果。
```

![Image 4](https://pic1.zhimg.com/v2-70c886f083385d86022276a34cfbc20e_1440w.jpg)

图 3：子任务可以分散完成，但最终必须经过总控汇总，形成一致、完整、可交付的结果。

一个完整的多智能体流程是：

```
1. 明确共同目标；
2. 按能力划分角色；
3. 各自完成分析或任务；
4. 交换中间结果；
5. 处理冲突和重复；
6. 总控统一收口；
7. Review 最终输出。
```

[多智能体协作](https://zhida.zhihu.com/search?content_id=281283924&content_type=Article&match_order=2&q=%E5%A4%9A%E6%99%BA%E8%83%BD%E4%BD%93%E5%8D%8F%E4%BD%9C&zhida_source=entity)的关键不是“人多”，而是：

> **能力互补，信息互通，责任明确，最终统一。**

* * *

## 四、第 10 讲与第 9 讲怎样连接？

第 9 讲提供组织执行的基础：

```
任务可以被拆分；
任务可以被下放；
结果可以被回收。
```

第 10 讲在此基础上增加认知协作：

```
不同角色可以提出不同观点；
中间结果可以相互影响；
多个判断可以被融合；
最终结果可以共同形成。
```

两讲合起来是：

```
第 9 讲：把工作分出去；
第 10 讲：把能力组织起来。
```

也可以写成：

```
Delegation 强调任务流；
Multi-agent 强调信息流与决策流。
```

* * *

## 五、什么时候不需要多智能体？

Multi-agent 不是越多越好。

简单任务如果也拆成五六个角色，反而会增加：

适合多智能体的任务通常具有这些特点：

```
问题复杂；
需要不同专业视角；
可以合理拆分；
结果值得交叉验证；
单个 Agent 容易遗漏。
```

简单读文件、改一行代码，单 Agent 往往更高效。

* * *

## 六、最小代码

```
opinions = {
    "tester": "失败来自空列表边界条件",
    "coder": "应在 mean() 中增加显式检查",
    "reviewer": "不应修改正确测试期望",
}

final_plan = [
    opinions["tester"],
    opinions["coder"],
    opinions["reviewer"],
]

print(final_plan)
```

这段代码表达的是：

```
不同角色贡献不同信息；
最终结果要经过整合，而不是简单并排输出。
```

* * *

## 七、这一讲让 Agent 长到了哪里？

到了第 10 讲，Agent 系统已经开始具备“小型工程团队”的形态：

```
有专业分工；
能并行观察；
能交换中间结论；
能相互检查；
能统一输出。
```

它不再只是一个强大的个体，而是开始具备组织多个认知角色共同解决问题的能力。

* * *

## 本讲小结

```
Subagent 解决“由哪些专业角色参与”；
Multi-agent 解决“多个角色怎样协同思考”；
多智能体不是凑人数，而是能力互补；
第 9 讲组织任务流，第 10 讲组织信息流和决策流；
群策群力以后，仍要由总控统一收口。
```
