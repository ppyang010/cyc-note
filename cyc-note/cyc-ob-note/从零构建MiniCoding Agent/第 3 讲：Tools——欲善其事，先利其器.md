# 第 3 讲：Tools——欲善其事，先利其器

> **欲善其事，先利其器。**

![Image 1](https://pic1.zhimg.com/v2-1d49b2b59f6ce5e593c5582420c9f184.jpg?source=25ab7b06)

前两讲里，我们已经给 Agent 立起了基本骨架：

```
第 1 讲：知道要做什么；
第 2 讲：知道怎样一轮一轮往前推。
```

但到了真正干活的时候，骨架还不够。

厨师就算拿着菜单、知道流程，如果没有刀、锅、秤和灶台，也做不出一桌菜。

Agent 也是一样：只有会说，不会真正动手，最后还是只能站在厨房门口当“嘴替”。

所以，第 3 讲只解决一个核心问题：

`Agent 靠什么真正把“想法”变成“动作”？`

答案就是：

`Tools（工具）`

![Image 2](https://pic4.zhimg.com/v2-b167706b4d075cc5932877e72d3f85d7_1440w.jpg)

封面图：这一讲的重点，不是“知道工具名”，而是“真的会把工具用起来”。

* * *

### 一、Tools 到底是什么？

在 Coding Agent 里，Tools 可以理解成它的 **手和脚**。

没有工具时，它只能：

```
猜问题在哪；
建议你去运行命令；
口头分析某个 bug 可能来自哪里。
```

有了工具以后，它才能真正：

```
打开文件；
读取目录；
运行命令；
查看输出；
修改代码；
再次验证结果。
```

换成做饭比喻也很好懂：

| 后厨里 | Coding Agent 里 |
| --- | --- |
| 菜刀、锅、灶台 | [文件工具](https://zhida.zhihu.com/search?content_id=279516033&content_type=Article&match_order=1&q=%E6%96%87%E4%BB%B6%E5%B7%A5%E5%85%B7&zhida_source=entity)、终端工具、[测试工具](https://zhida.zhihu.com/search?content_id=279516033&content_type=Article&match_order=1&q=%E6%B5%8B%E8%AF%95%E5%B7%A5%E5%85%B7&zhida_source=entity) |
| 真正下厨 | 真正执行任务 |
| 尝味道、看火候 | 看输出、看结果 |

![Image 3](https://pica.zhimg.com/v2-85a5467aa6907b3154ce5f05ee71810c_1440w.jpg)

图 1：文件、终端、测试三类工具，就像后厨里的基础厨具。没有它们，Agent 只能空想。

* * *

### 二、最常用的三类工具

如果把一个 Agent 放进真实项目，它最常碰到的工具，通常就三类：

```
文件工具：读文件、写文件、看目录结构；
终端工具：跑命令、看输出、管理环境；
测试工具：运行测试、复现问题、验证修复。
```

继续用 `enhanced_project` 这个贯穿案例来说：

```
先用终端工具跑 pytest；
看到 4 failed, 6 passed；
再用文件工具打开对应源码；
修改 add()、mean()、median()、format_percentage()；
最后再用测试工具验证，直到 10 passed。
```

这里有个非常关键的认识：

> **工具不是装饰，而是 Agent 真正干活的入口。**

没有工具，它连“看现场”都做不到。

有了工具，它才开始具备真正的执行力。

* * *

### 三、工具调用不是说一句“我来用工具”

很多人一听 Tool Call，会误以为是模型在脑子里想一下：

`“我现在应该用 read_file。”`

这还不够。

一次真正有效的工具调用，至少要有三步：

```
选工具：现在该看文件，还是跑命令？
执行：真的把动作做出来；
看结果：拿到 Observation，再决定下一步。
```

![Image 4](https://pic1.zhimg.com/v2-74e04fb373fe0cf40ad5a01ea33f21c6_1440w.jpg)

图 2：工具调用不是一句话，而是一个小闭环：选工具 → 执行 → 拿结果。

举个最朴素的例子：

```
问题：测试为什么失败？
→ 用终端工具跑 pytest
→ 得到失败输出
→ 根据输出，再用文件工具打开源码
→ 继续做下一步判断
```

如果只“宣布要调用”，却没有真实返回结果，那它本质上还是在想象。

* * *

### 四、为什么“会用工具”比“会分析”更重要？

因为工程现场不奖励“分析得像”，而奖励“验证得准”。

只会分析的 Agent，常见毛病是：

```
不看文件就下判断；
不跑命令就给建议；
不看测试结果就说已经修好了。
```

这就像厨师不尝味道就说菜熟了，不看火候就说汤没问题。

真正像样的工程习惯，应该是：

> **少猜一点，多验证一点。**

![Image 5](https://pic1.zhimg.com/v2-732b48f5f2ecdb8afd6e6073d942bc02_1440w.jpg)

图 3：左边是“只会想”，右边是“真正动手”。工程里，后者才有推进能力。

所以，第 3 讲真正要建立的，不是一串工具名，而是一种做事习惯：

```
能读文件，就别纯靠猜；
能跑命令，就别只靠想；
能看结果，就别急着下结论。
```

* * *

### 五、最小代码只需要表达一个意思

这一讲暂时不把工具系统写复杂。

最小代码只需要表达：

```
选一个工具；
给它输入；
拿回结果。
def use_tool(tool_name, arg):
    print(f"调用工具: {tool_name}")
    print(f"输入参数: {arg}")
    return f"工具返回结果: {arg}"

result = use_tool("read_file", "stats.py")
print(result)
```

这段代码很简单，但足够把第 3 讲的骨头立起来：

`工具调用 = 选择工具 + 提供参数 + 获得结果`

后面我们再逐步把更完整的文件、终端、测试能力接进来。

* * *

### 六、这一讲让 Agent 长到了哪一步？

如果用 L0～L5 的成长阶梯来放，第 3 讲是一个很关键的过渡：

```
L1：只会围绕局部代码说建议；
L2：能接任务、拆步骤、维护状态；
L3：开始真正调用工具，持续往前推进。
```

也就是说，到这一讲，Agent 才真正像一个刚进后厨的新手厨师：

```
不只是会背菜谱；
还开始会拿刀、会开火、会试做。
```

* * *

### 本讲小结

第 3 讲只记住四句话就够了：

```
Tools 是 Agent 的手和脚；
文件、终端、测试，是最常见的三类工具；
工具调用要有输入，也要有结果；
少猜一点，多验证一点。
```

下一讲我们继续补上一个很现实的问题：

> **会用工具，不等于可以随便乱用。**
