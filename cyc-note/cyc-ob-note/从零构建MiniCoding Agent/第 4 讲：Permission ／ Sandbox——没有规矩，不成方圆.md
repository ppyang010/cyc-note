# 第 4 讲：Permission / Sandbox——没有规矩，不成方圆

> **没有规矩，不[成方圆](https://zhida.zhihu.com/search?content_id=279516468&content_type=Article&match_order=1&q=%E6%88%90%E6%96%B9%E5%9C%86&zhida_source=entity)。**

![Image 1](https://pica.zhimg.com/v2-ee886aac83b29ffb314b3c08da9e3d8d.jpg?source=25ab7b06)

第 3 讲里，我们给 Agent 配上了真正的工具。

现在它已经能：

```
读文件；
跑命令；
看测试结果；
修改代码；
继续推进任务。
```

但工具一拿到手，新的问题马上就来了：

```
哪些动作可以直接做？
哪些动作要先确认？
哪里可以先试？
哪里不能乱碰？
```

这就是第 4 讲的主题：

```
Permission：权限 / 确认机制；
Sandbox：沙箱 / 安全边界。
```

如果说第 3 讲是在教 Agent “拿起锅铲”，

那第 4 讲讲的就是：

```
什么时候能开火；
什么锅不能乱掀；
哪些操作要先问一句；
哪些练习该先在小灶台上做。
```

![Image 2](https://pic1.zhimg.com/v2-0ea366dd9b49200761e008e579a7a9c4_1440w.jpg)

封面图：第 4 讲的重点不是“把 Agent 关住”，而是“让它安全、稳当地做事”。

* * *

### 一、为什么不能“想做什么就做什么”？

因为真实工程不是游乐场。

很多动作，一旦做错，后果就不是“再试一次”这么简单。比如：

```
直接删除文件；
覆盖关键配置；
重置数据库；
执行高风险脚本；
修改正式环境里的内容。
```

这些动作就像后厨里的高温锅、总电闸、蒸汽阀门：

不是说永远不能碰，而是不能想碰就碰。

所以，一个成熟点的 Agent 必须知道三件事：

```
哪些事可以直接做；
哪些事要先确认；
哪些事现在不能做。
```

![Image 3](https://pic3.zhimg.com/v2-d901e03cde8891a37966a52269e65a80_1440w.jpg)

图 1：Permission 的核心，是先分清风险，再决定能不能做。

第 4 讲最朴素的一句话就是：

> **不是不能做，而是先确认能不能做。**

* * *

### 二、Permission：先问清楚，再动手

最简单的理解方式，是把动作分成几层：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 低风险操作 | 读文件、看日志、查目录 | 可直接做 |
| 中风险操作 | 改代码、运行可能改状态的命令 | 谨慎执行 |
| 高风险操作 | 删除、覆盖、重置、影响正式环境 | 先确认，再执行 |

放到做饭场景里，也很自然：

```
看菜单、拿餐具，可以直接做；
动刀、开火，要更小心；
启动高温高压设备，最好先确认。
```

Permission 解决的，其实不是“会不会做”，而是：

`我现在这个动作，到底有多大风险？`

这一步一旦省掉，Agent 就容易从“能干活”直接滑到“乱干活”。

* * *

### 三、Sandbox：先在安全区里练手

有些事不是不能做，而是最好 **先在安全环境里做**。

这就是 Sandbox 的意义。

![Image 4](https://pic2.zhimg.com/v2-279fcc236d3d100c2e2706ddf5fbb83d_1440w.jpg)

图 2：Sandbox 像一个练习小厨房。先试、可回退、不伤正式环境。

一个像样的 Sandbox，至少意味着三件事：

```
可试验：先做一次看看会发生什么；
可回退：如果做错了，能撤回来；
不伤正式环境：不会把真实系统一起带坏。
```

继续用 `enhanced_project` 的例子来想：

```
先在当前项目副本里改代码；
先跑本地测试；
先看 diff；
先确认结果；
再考虑进入更正式的环境。
```

这就像后厨里的练习灶台：

先在安全区域试菜，不要一上来就把正式宴席端上实验。

* * *

### 四、为什么“有边界”反而更高效？

很多人直觉会觉得：

`边界越少，动作越快。`

但工程里的真实情况常常正相反。

没有边界时，最常见的问题是：

```
顺手误删；
改错地方；
返工重来；
出了问题还找不到是哪一步出的问题。
```

有边界时，反而更清楚：

```
什么能直接做；
什么要先确认；
什么先在沙箱试；
什么绝对不能碰。
```

![Image 5](https://pic3.zhimg.com/v2-7233859b095729206fac5e11fb5b19f2_1440w.jpg)

图 3：左边是“没规矩”，右边是“有边界”。前者看着自由，后者反而更稳。

所以边界不是拖慢效率，而是减少低级错误、减少返工、减少事故。

* * *

### 五、最小代码只需要表达“先检查，再执行”

这一讲也不需要把权限系统写复杂。

最小代码只要能表达一个意思：

```
先判断动作风险，再决定能不能执行。
def can_run(action):
    high_risk = ["delete_file", "reset_db"]
    return action not in high_risk

action = "delete_file"

if can_run(action):
    print("允许执行")
else:
    print("需要确认后再执行")
```

这段代码虽然很小，但已经把第 4 讲的骨头搭出来了：

```
不是所有动作都默认放行；
高风险动作，要先过一道确认。
```

* * *

### 六、这一讲让 Agent 更像“靠谱的新厨师”

把前四讲放在一起看，其实是一条很顺的成长线，到了这里，Agent 开始有一点“能进后厨干活”的味道了：

```
不只是会说；
不只是会做；
还知道什么时候该停一下，先确认，再动手。
```

这就是从“会干活”向“干得稳”迈出的一步。

* * *

### 本讲小结

第 4 讲只记住四句话就够了：

```
Permission 解决“能不能做”；
Sandbox 解决“先在哪里做”；
高风险动作要先确认；
边界不是束缚，而是减少出错。
```
