我兴冲冲把 Opus 4.6 换成 Opus 4.7，想着这波稳了，结果用了一天，人直接懵了。  
  
体感不是"变强了"，是"变陌生了"。  
  
同样的 prompt，老模型乖乖干活，新模型要么直接给我跳过步骤，要么自己生成一堆我没让你生成的子代理。  
  
我第一反应是，卧槽是不是 prompt 写的有问题，然后开始疯狂加细节、加约束、加"请一步一步来"。  
  
越加越乱。  
  
直到我去翻了 Boris Cherny 写的那篇 Opus 4.7 使用指南。  
  
Boris Cherny，Claude Code 的作者，就是写那个让 Claude 可以自动跑几个小时不用盯着的工具的人。  
  
他拿到 Opus 4.7 之后也是人傻了，花了几周才摸清楚门道。  
  
他原话是这样的：4.7 在 token 用量和行为上，会因使用方式不同而有显著差异。  
  
翻译成人话就是，你不能拿用 4.6 的方式去用它，不然要么浪费钱，要么被气死。  
  
先说一个最反直觉的事。  
  
Opus 4.7 比起 4.6，最核心的变化不是"更强了"，是"更 autonomous 了"。  
  
Boris 的说法是你得把它当一个可以独立完成任务的工程师来对待，而不是一个需要你逐行指导的搭档。  
  
这话听着简单，但我跟你说，真的操作起来，这个思维转换比想象中难太多。  
  
为什么？  
  
因为我们这代程序员从小被训练出来的习惯是"我要控制每一步"。  
  
你翻开教科书，都是教你怎么写精确的指令、怎么拆解任务、怎么验证输出。  
  
你用 Git Copilot，也是给它一个提示，它给你补一行，你不满意再改。  
  
这种工作方式在 Opus 4.6 时代还能用，到了 4.7 你会发现一个问题。  
  
你越是试图控制它，它越容易"想太多"。  
  
Boris 说了，4.7 在高 effort 等级下会自己判断哪些地方需要深入思考。你如果不停插嘴"等一下先做这个再那个"，它就得在每一轮都重新推理一遍。  
  
结果就是，你的 token 消耗比 4.6 还高，但输出质量反而不如预期。  
  
这跟我们平时说的"少管闲事"还不一样。  
  
这次是"少管 AI 的闲事"。  
  
顺着这个说一个具体的坑。  
  
Boris 提了一个建议，我看完直接愣住了。  
  
他说，你应该减少中间的交互次数。  
  
什么意思呢？就是你不要像这样：问一句、等回复、再问一句、再等回复。  
  
你得把问题打包，一次性说清楚。  
  
他说，信息越完整，输出质量越高；模糊的任务分散在多轮对话里传达，既浪费 token，也可能降低质量。  
  
这话要是搁以前我肯定跳起来反驳，程序员谁不是边问边调的？  
  
但 4.7 真的不一样。  
  
你每说一句话，它都会触发额外的推理开销。多轮下来，token 消耗是一个方面，更重要的是它可能会偏离你的原始意图。  
  
所以 Boris 的建议是，从第一条消息开始就把任务说清楚，包括你的意图、约束条件、验收标准、相关文件位置。  
  
他说得比较文绉绉，我给你翻译一下，就是"第一条消息决定一切"。  
  
这感觉很反模块化编程的思想，但这不是写代码，是跟一个能自主推理的 agent 协作。  
  
Boris 还提了一个更骚的操作。  
  
他说你可以让 Claude 在完成任务时播放声音，它会自动创建基于 hook 的通知机制。  
  
我当时看到这儿就想，这不就是让 AI 打工的时候给自己放"工作顺利"的BGM吗。  
  
但仔细一想还真有道理，你让一个自主任务跑起来，不用盯着了，直接切去搞下一个任务，回来的时候听声音就知道完没完成。  
  
这种工作流，4.6 真的做不到。  
  
然后说 effort 档位。  
  
Boris 给了一个表，我直接说结论。  
  
xhigh 是默认值，适合大多数编程和自主任务。  
  
low 和 medium 是对成本和延迟敏感、但任务范围明确的场景，就算同等 effort 下表现也优于 4.6。  
  
max 是真正高难度问题，或在 eval 中测试模型上限用。  
  
他个人的用法是，大多数任务使用 xhigh，最难的任务才上 max。  
  
但他也说了，max 只对当前 session 生效，其他 effort 档位则会延续到后续 session。  
  
也就是说，你如果想在不同任务之间切换 effort，得手动调。  
  
这个细节我之前完全忽略了，每次都是一股脑往 max 冲。  
  
说实话，max 真的存在收益递减，你花的钱可能是 xhigh 的两倍，但换来能力的提升可能只有 10%。  
  
所以这玩意儿不是你使劲越大越好的。  
  
你信我。  
  
然后说一个我之前完全不知道的东西。  
  
Opus 4.7 不再支持固定思考预算的 Extended Thinking，取而代之的是 Adaptive Thinking。  
  
模型可以在每个步骤自行决定是否需要思考，简单的查询直接回答，需要深入推理的步骤才会投入更多 thinking token。  
  
这个版本的 adaptive thinking 比之前明显改进，过度思考的问题得到了改善。  
  
也就是说，4.6 时代你可能还得手动控制它"想多少"，4.7 基本上自己就能判断。  
  
如果你想控制它想多还是想少，可以直接在 prompt 里说。  
  
想要更多思考，就加上"在回答之前请仔细一步步思考，这个问题比看起来更难"。  
  
想要更少思考，就加上"优先快速回答而不是深度思考，有疑问时直接给出答案"。  
  
第二个可能会损失一些准确性，但省 token。  
  
这个控制方式比之前那种设置 budget\_tokens 的方式直觉多了。  
  
你不需要知道背后是什么机制，你只需要告诉它你想要快还是想要准。  
  
说到这儿我要插一句，Boris 整篇文章最强调的一点，我单独拿一节来说。  
  
他说，你一定要给 Claude 一个"验证自己"的手段。  
  
这句话可以让 Opus 4.7 的效果提升 2 到 3 倍，在 4.7 上更重要。  
  
验证方式会根据任务类型不同而不同。  
  
做后端的时候，要让 Claude 能启动服务并完成端到端测试。  
  
做前端的时候，可以通过 Claude 的 Chromium 扩展让它直接控制浏览器。  
  
如果是桌面应用，可以使用 computer use。  
  
Boris 他现在很多 prompt 会写成类似"Claude 做某件事，然后/go"。  
  
这个 /go skill 会让 Claude 自动完成一整套流程，先通过 bash、浏览器或 computer use 做端到端自测，然后运行 /simplify skill，最后直接提交 PR。  
  
我当时看到这个就想，这不就是让 AI 自己跑、自己测、自己上线吗。  
  
如果这套流程真的能跑通，那一个人干一个团队的活还真不是吹的。  
  
但我也要说，这个要求其实挺高的。  
  
你需要有完整的测试环境、有可执行的验证脚本、有可信的 CI/CD 流程。  
  
这不是 AI 本身的问题，是你自己的工程基础设施够不够扎实的问题。  
  
所以这个方法听起来很爽，但用起来肯定有学习曲线。  
  
一开始可能会比较笨拙，花的时间比手动做还长。  
  
这不是泼冷水，是实话说。  
  
最后说一个我看完 Boris 文章之后最大的感触。  
  
他说，Opus 4.7 的提升是明显的，但变化不只在模型本身，也在使用方式上。  
  
你如果还是沿用旧 workflow，当然也能感受到它比上一代更强。  
  
但只有把工作方式一起调过来，真正利用它"能跑更久、agent 性更强"的特点，这一代的差距才会被真正拉开。  
  
我读完这句话就想到了相机。  
  
你给一个只会用自动模式的人一台专业相机，他拍出来的照片大概率还不如手机。  
  
不是因为相机不好，是因为他没用对方式。  
  
Opus 4.7 也是一样，它本质上是一个更强大的 autonomous agent，不是更快的打字机。  
  
你如果还是把它当"更聪明的代码补全工具"用，你能感受到的变化就是"它回复的字多了点"。  
  
但如果你开始把它当"可以独立负责一个模块的工程师"用，那才是真正的分水岭。  
  
这个切换的过程肯定不会一蹴而就。  
  
你信我，我自己也还在摸索。  
  
但有一点是确定的，就是这次升级真的不只是性能数字的变化。  
  
这是一次工作方式的范式转移。  
  
就像当年从手动对焦到自动对焦，从胶片到数码。  
  
你不能只是"更用力地使用旧方法"来适应它，你得接受它是一个新物种，然后用一种新的方式跟它协作。  
  
这个切换的成本是真实的，但切换之后的收益也是真实的。  
  
问题只是，你愿不愿意花这个时间。
