因为 JDK 9 开始采用了新的字符串存储方案，对于能以 Latin-1（ISO/IEC 8859-1）编码表示的字符串就以单 `byte` 存储， 包含其他字符的字符串再转而像以前那样用 UTF-16 编码来存储，靠这种双编码并存的方式减少内存占用，以及提高性能。

在 Java 9 之前，JavaScript 的 V8 就已经用类似的方式存储字符串了。

这种存储方式一方面内存占用不再比 UTF-8 更高（不少场景比 UTF-8 还低），一方面还能享受到 UTF-16 的“伪定长”的优势，处理起来更方便，我个人认为这算是目前很优秀的字符串实现方案了。

在展开讲解这种字符串存储方式的优势之前，我想先给 UTF-16 正一下名。

## 插话：为 UTF-16 正名

如果你对 Unicode 所有了解的话，你应该知道 UTF-16 是一个变长的编码，对于 emoji 等不太常用的字符码点（Code Point）需要两个 2 字节的码元（Code Unit）组成代理对（Surrogate Pair）来表示。

因为常用字符基本都是用一个码点就能表示，导致很多对 UTF-16 认识不到位的程序员误把它当作定长编码，把 Java 的 `char` 当成字符来对待，导致 Unicode 码点可能会被从中间截断，这一点让它被包括我在内的很多人诟病。

但在进一步了解 Unicode 后，我现在认为 UTF-16 是一个很好的折衷选择，变长这个问题并不是很严重。

为什么这么说呢？我们可以想一下我们现在处理字符串的方式。

目前认可度最高的处理 Unicode 字符串的方式是不管字符串用什么编码存储，处理时都转换成 Unicode 码点，存储在四字节的整数变量中进行处理。

这种处理方式看起来相比用 UTF-16 码元处理字符更好，解决了代理对的截断问题，但它真的解决了截断问题吗？其实并没有。

由于 Unicode 可以把几个码点放在一起组合成一个符号，所以用户眼中的“字符”通常也不是 Unicode 码点，而是字素簇（Grapheme Cluster）。

举个例子，`ā` 这个字符就是 `a` 和 U+0304 这个组合附加符号（Combining Diacritical Marks） 放在一起构成的，我们可以看到它不管按 UTF-16 码元还是按照 Unicode 码点统计，都是两个“字符”：

```console
jshell> "ā".length()
$1 ==> 2

jshell> "ā".codePoints().count()
$2 ==> 2
```

到了 emoji，多个码点组合成一个字符的情况就更多了。

国旗 emoji 就是用 `U+1F1E6` 到 `U+1F1FF` 的 26 个区域指示符代表 A~Z 的二十六个字母，然后用两个区域指示符拼出国家地区代码来表示国旗。比如 CN 就是（`U+1F201 U+1F20C`）。

除此之外，还有 `U+200D` 这个 ZWJ（零宽连字符，Zero-Width Joiner）字符，可以作为分隔符把一串码点连在一起，一个经典例子就是把 这四个 Emoji 两两之间用 ZWJ 串起来，就能组合成

![](images/454_001.png)

这样一个由 7 个 Unicode 码点连接而成的 Emoji 字符：

```text
jshell> String woman = Character.toString(0x1F469), girl = Character.toString(0x1F467), boy = Character.toString(0x1F466)
woman ==> " "
girl ==> " "
boy ==> " "

jshell> var ZWJ = '\u200D'
ZWJ ==> ''

jshell> var family = woman + ZWJ + woman + ZWJ + girl + ZWJ + boy
family ==> ""

jshell> family.length()
$1 ==> 11

jshell> family.codePoints().count()
$2 ==> 7
```

到这里我们可以看出来，虽然把 UTF-16 假装成定长编码的做法确实处理不好 Emoji，但按码点来处理同样解决不了问题。

虽然现在有 Swift 珠玉在前，但新语言也很少在字符串上做正确的事，毕竟愿意在字符串这个很基础的功能内部牵扯进大量 Unicode 相关的细节多少让人有些头疼，用起来也不是特别方便，按字素簇处理字符串不仅麻烦而且性能低下，相对而言将“字符串”和“文本”分开处理的话心智负担反而可能低一些。

在了解了这些背景后，是不是在把 UTF-16 当定长编码来用时的负罪感低了很多？

这时我们会发现 UTF-16 其实是一个很好的折衷选择，相比 UTF-32 内存占用低得多，相比 UTF-8 又能在更多场景里假装自己是定长编码来得到随机访问的能力，因此处理起来更灵活。

## 正题

说了这么多离题的话，现在让我们回到问题上，详细谈谈为什么 Java 会选择 Latin-1 和 UTF-16 并存的存储方案，这为 Java 带来了什么。

### 为什么是 Latin-1？

用一个字节来表示一个字符的编码其实有很多，最经典的当然就是我们熟知的 ASCII，除此之外还有 Latin-1（西欧语言字符集）、Latin-2（中欧语言字符集）、Latin-3（南欧语言字符集）等等。

由于 ASCII 只定义了 128 个字符，用有 256 个不同值的 byte 来存储的话实在是太浪费了，所以人们又创造了 Latin-1 等兼容 ASCII 的单字节编码，把 byte 剩下的 128 个值都利用上。

相比其他单字节编码，Latin-1 有着一个巨大的优势：它刚好对应了 Unicode 的前 256 个码点，比如 Latin-1 的 0xFF 字符 `ÿ` 就是 Unicode 中的 `U+00FF` 这个字符。 这意味着将一个 `byte` 表示的 Latin-1 字符转换成 Java 的 `char` 或者用于表示 Unicode 码位的 `int` 时根本不需要复杂的映射，直接强制转换就行。由于这个原因，Latin-1 是不可替代的。

### 内存占用

相对于 UTF-8 来说，UTF-16 的内存占用一直是被人诟病的地方。

不同类型的字符以 UTF-8 编码时占用的内存大概是这样：

-   ASCII 字符：1 字节
-   欧洲语言字符：2 字节
-   中日韩常用字符：3 字节
-   Emoji：4 字节

而用 UTF-16 编码时大概这样：

-   ASCII 字符/欧洲语言字符/中日韩常用字符：2 字节
-   Emoji：4 字节

其实这样看，UTF-16 也并不总是比 UTF-8 更浪费空间，尤其是对于以中日韩文字符为主的情况下 UTF-16 比 UTF-8 还要省空间，但毕竟程序中 ASCII 还是占大头，所以 UTF-16 通常还是会比 UTF-8 更浪费内存。

但在 Java 在引入 Latin-1 作为单字节编码后情况就完全不同了：

-   ASCII / 西欧语言字符：1 字节
-   其他欧洲语言字符/中日韩常用字符：2 字节
-   Emoji：4 字节

这种混合方案结合了 Latin-1 和 UTF-16 的优点，不仅存储纯 ASCII 文本时不再比 UTF-8 占用更高，而且对于 ASCII 混西欧字符的文本以及以中日韩字符为主的文本比 UTF-8 更省内存。

虽然在 ASCII 为主混有少量中日韩字符的时候还是比不过 UTF-8，但比 UTF-8 更好的情况也不少见（尤其是对于西欧和东亚用户），综合来看可以说这种混合方案内存占用方面不逊于 UTF-8。

### 性能

由于两种编码的共存，一些操作会产生额外的开销，比如 `StringBuilder` 就需要额外的工作来记录当前使用的编码，并在必要时将内部以 Latin-1 编码存储的字节数组“膨胀”成 UTF-16。

这些开销虽然不可避免，但内存占用的减小代表着对缓存更加友好，除此之外也有一些知识能够进行一些以前无法做到的优化：

-   针对 Latin-1 可以利用一些“古老的 ASCII 技巧”（比如用 `ch & 0xdf`/`ch | 0x20` 进行大小写转换） 针对性的优化，Java 21 中就包含了一些这样的优化；
-   Latin-1 是定长编码，因此可以优化部分基于 Code Point 的操作；
-   Latin-1 编码的字符串中不会包含无法被 Latin-1 编码的字符；
-   只需要扫描 Latin-1 编码的 `byte[]` 中是否包含负数就能确定它是不是纯 ASCII 字符串，能够与 UTF-8 等编码直接兼容；
-   只需要扫描 UTF-8 编码的 `byte[]` 中是否包含负数就能确定它是不是纯 ASCII 字符串，能够与 Latin-1 直接兼容。

这些知识都有助于优化 Latin-1 字符串各类操作的性能，从而弥补了两种编码方式共存导致的那些不可避免的开销，最终除了极少数情况会有性能下降，大多数时候不仅没有牺牲性能，还会有性能上的进步。
