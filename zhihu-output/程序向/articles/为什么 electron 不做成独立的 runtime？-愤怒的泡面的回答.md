我以前在 electron 的 issue 列表看到过一个 discussion 提到过类似的建议，个人觉得从技术上其实是完全可行的。比如说每次发布的时候只发布 .asar, 不再随着 electron 本体进行打包，electron 将作为一个独立的运行时提供 API.

这个想法相当棒，某种程度解决了 electron 应用发布体积过大的问题。不过我能想到的有几点顾虑，不知道是不是也是开发团队的顾虑：

比如说，electron 的版本迭代非常快，小版本很多，尤其是面对前端复杂的生态，如果作为运行时发布，必将会面对大量的小版本差异和兼容性问题，并且跨了多个平台，我觉得维护起来应该相当复杂，违背了它具备跨平台一致特性这个大优点。

如果这么做了，这时候就会面临以下问题：

1.  开发者来指定可以跑的运行时版本范围，这样会极大增加开发者的负担，增加开发者的测试难度，如果你是 Electron App 的开发者，你可能不愿意做这么繁琐的工作；
2.  由开发团队来做好运行时的版本兼容问题，假使你小版本通过某种规范，让开发者可以不考虑 API 的兼容问题，但这样无疑也会大幅度增加前向兼容的负担，时间久了，一定会有不小的历史包袱，作为开源项目我个人觉得并不适合这样做；
3.  如果系统没有匹配的版本的运行时，这时候最先能想到的方式就是通过自动下载，或者通过其它渠道按照对应版本的运行时，这样系统里的运行时也会越来越多，比起 electron 本体的几十 MB 体积，似乎也并没有解决问题；
4.  最重要的一个问题，Electron App 的数量其实也并没有那么多，社区可能还没有足够的动力去做；

综上所述，虽然我很希望有这样的东西，但我认为这仍然是个很复杂的工程。其实以现在的带宽来考虑 electron 的体积，已经不是什么大问题了，除非有特殊需要，否则我觉得用户其实并不在意30M的体积。

目前 Windows 有一大堆的 VC++ 运行时，可能也会被间接要求安装 Python, Java, .Net，你可能不会直接用到，如果作为普通用户，我觉得他们如果懂的话，也肯定不希望安装一大堆不同版本的运行时，即使你的 App 已经被卸载了，他们也还在你的机器上。

如果我是开发者，我更偏向用户多花十几秒下载我的应用，然后就能直接打开，并且几乎不会有什么兼容问题。而不是希望他们下载了东西之后，还要面临可能出现的运行时下载，或者用户为了找运行时，也很难预测他们会通过什么渠道去打上这个 patch, 反而增加了他们的风险（比如说找VC++运行时送了一堆全家桶）。

但我仍然很希望有那么一天，electron 应用也可以像 .NET/VC++ 程序一样使用广泛，这样我上面脑补到的问题，其实也都不是问题了。
