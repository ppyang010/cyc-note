实际上 OpenJDK 社区认为有必要在标准库中集成 JSON 支持，但不是现在。

现在 Java 还处于快速发展的阶段，比如近期引入的模式匹配就是相当重磅的语言功能，解构模式等重要特性也是纷至沓来。

OpenJDK 社区还在等待几个重要的语言演变，在这之后再讨论具体怎么设计一个更现代化的 JSON 库。

* * *

对于把已有的被广泛使用的第三方库的功能集成进标准库这种事情，早期 Java 也做过一些尝试，但并不是很成功（比如 java.util.logging），且暴露了一些问题，最后导致的现在的 OpenJDK 社区在这方面很保守。

Java 标准库相比大部分来自社区的第三方库，维护模式、发布周期等方面都有很大的不同：

-   Java 标准库通常只会在大版本更新时提供新的 API。这个大版本更新周期在 Java 9 之前长达 2~5 年，虽然从 Java 9 缩短了稳定为半年，但往往每隔三年（从 Java 21 开始是两年）发布的 LTS 版本才会被广泛采用；相对而言第三方库的更新要敏捷很多，更新次要版本号甚至修订号的时候就能引入新功能，发布周期往往只有几个月甚至更短；
-   Java 对 API 兼容性有着非常严格的要求，API 行为不兼容的变化只会在大版本更新时进行，而且每个变化都会受到非常严苛的审查，因此非常罕见；像 JPMS（Java 模块系统）这种会存在相当破坏性的变更，即使在 Oracle 的强力推动下也是阻力重重，推迟了六年才终于进入了 Java 9；而第三方库很多甚至在只更新次要版本号的情况下就能做出一些不兼容变化；
-   作为对兼容性的保障，Java 标准库 API 从弃用到移除通常需要 5~10 年，还有一些 API 被弃用后就放在那了二十年也不准备彻底移除。

由于维护模式、发布周期等方面巨大的不同，标准库的更新做不到像第三方库那么敏捷，且做出来的新功能要被行业广泛接纳使用也需要短则两三年长则十余年的时间。

引入标准库的 API 任何缺憾都需要极长的时间去弥补，甚至是永远都解决不了，因此社区在极力避免将第三方库能够实现的功能在条件不成熟的时候引入标准库中。

了解这些后，我想大家虽然对 OpenJDK 社区的保守就算有所怨念，但也能够理解一些了。

* * *

说完这些让用户多少有些不爽的事后，再来说说好消息。

事实上，从 JDK 9 开始，Java 的发展已经大大提速了，以上这些问题也开始缓解。

固定半年的发布周期以及更开放地拥抱社区的姿态都是老生常谈的事情了，今天我在这里说说模块系统以及预览/孵化器特性对标准库发展的影响。

在模块系统到来之前，虽然只有 `java`/`javax` 包下的内容属于真正的 API，但由于没有检查和限制，当时很多库和应用对 `com.sun` 等包内的 JDK 私有类的使用相当野蛮（点名某方块游戏的某模组加载器）。

模块系统解决了这些问题，它让 API 和私有类泾相分明，约束了用户的使用方式，也减轻了 JDK 维护者的负担，让开发者可以更自然地对这些实现细节进行随意地更改。模块系统的封装保护也能让 JDK 开发者更少顾虑用户代码破坏 JDK 完整性，因此可以更自由地在 JDK 内部跨包开放共享一些私有功能。

而预览/孵化器功能的引入对于 Java 发展也有着很大的正面影响。

在此之前，很多功能都是 Sun/Oracle 闭门造车，隔几年憋个 Java 大版本，把一堆功能作为稳定特性一股脑推出。这个过程中只有社区内部反馈，缺乏大量实际用户反馈，等用户实际遇到问题的时候已经太迟了，很多东西都无法再去修改。

为了解决这些问题，随着 JDK 9 开始加速的发版周期，OpenJDK 也推出了预览特性和孵化器模块，从而允许 JDK 提供某些公开但是不保证兼容性的功能。

预览特性和孵化器模块出现后，Java 新的重要功能通常都需要经过至少两个版本的预览阶段。

预览阶段的存在一方面可以让 Java 在功能在稳定之前就开始宣传尝鲜，加速新功能的推广，一方面解决了之前闭门造车的问题，把原本在社区或者公司内部对功能的推敲公开，更早的把功能亮出来让实际用户参与反馈，可谓意义重大。

* * *

本来想说到这里就结束了，但回头看了看，我觉得还是要补充说明一下社区现在正在进行的工作，不然显得有些敷衍。

我再强调一下，这篇回答前面的内容都是很认真的，不是敷衍的套话。JSON 类库在近期刚被社区重新讨论过，确认是将要进行的工作之一，只是现在还不是高优先级事项。

目前 OpenJDK 标准库中正在积极开发的是字节码框架 [ASM](https://link.zhihu.com/?target=https%3A//asm.ow2.io/) 的现代化替代品：[Class-File API](https://link.zhihu.com/?target=https%3A//openjdk.org/jeps/8280389)。

Class-File API 是全新设计的现代 API，依赖于模式匹配，相比大量使用 visitor 模式的 ASM 更优秀易用。

Class-File API 的实现已经进入 Java 21 的 `java.base` 模块内部，JDK 已经将大量原先使用 ASM 的功能迁移至新的 Class-File API 上。

因为该 API 还没开始 Preview，所以它的实现在 `jdk.internal.classfile` 这个内部包中，现在用户无法直接使用它。我将它的实现提取了出来，移植回 Java 17 并发布在 Maven Central 上，提供想要尝鲜的用户使用，遇到问题或者有改进建议也可以直接通过邮件列表 ([classfile-api-dev@openjdk.org](mailto:classfile-api-dev@openjdk.org)）进行反馈。

[Glavo/classfile: A modern Java classfile manipulation and analysis library](https://link.zhihu.com/?target=https%3A//github.com/Glavo/classfile)

当 Class-File API 完成后，Java 语言的几个语法演进应该也已经完成，到那时也该开始对新 JSON 库的设计方案进行讨论了。

OpenJDK 社区不会满足于仅仅是将现有的类库搬进标准库，而是会尝试吸取现有方案的经验，设计更现代化的类库。为了让设计更接近完美，请再耐心等一等。
