我是觉得主要是思维方式不同，了解一点软件工程的历史应该会知道到上世纪九十年代后期到零零年代那会儿 Java 可以说就是软件工程这门学科的“指定编程语言”，有些类似于 Haskell 之于 PL. 那会儿软件工程的方向就是规模化、企业化，尽可能解耦，能够拆分就拆分，试图把所有东西搞成松散耦合的、可配置的，而敏捷开发、TDD 这种东西是后来出现的了。

你至今还能在一堆软件工程的课程资料、书籍中看到一堆恐怕永远也不能得到实用的、并且早就没人继续研究的实验性架构，它们试图用 UML 和各种 DSL 去描述软件，试图将每一行代码约束在严密的设计流程中——有点像是现在日本外包软件的思路。而 Java 本身毫无疑问受到了这种影响，因此也极其强调可灵活配置、松散耦合的概念。换句话说，Java 生态中很多东西压根就不是从“程序员”的角度去考虑的，而是从一个纯粹的更高视角的架构师层面、甚至是软件工程学者的层面去考虑的。自然，一切可能导致软件耦合度提高的东西都是不鼓励的，一切降低耦合度的尝试都是推崇的。而依赖注入很明显非常符合这一思路……

后来许多编程语言的许多框架，更多是程序员和工程师在主导，更加偏重实用性，而不会极端强调架构上的松散以至于带来太多实现上的麻烦。Go 本身就是一门工程师味很重的语言，生态中的很多框架也是程序员们自己在开源社区捣鼓，并没有形成太多规范化的开源团队，自然是以实用性优先。至于 C++……当年 Java 出来的一大原因就是嫌弃 C++ 太复杂，所以软件工程的那一套东西自然就没太影响到 C++ 生态，这使得 C++ 一直以来都是那门底层程序员的编程语言，而不是“架构师和研究者们”的编程语言……

其实现在分得也不是那么清楚了。Spring 生态现在也在逐渐去配置化，MyBatis 都不那么鼓励写 XML 了。包括一些前端的趋势，很多框架似乎在有意的“去模块化”，或许这更多说明了追求“简洁即易维护”的程序员思维在逐渐起到作用。相比于架构层面的 Expressive 和 Flexibility，人们似乎逐渐更青睐于代码本身的 Expressive 与 Intuitive.
