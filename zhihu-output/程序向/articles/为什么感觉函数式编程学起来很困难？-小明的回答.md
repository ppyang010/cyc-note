我认为其根本原因在于，看得太多，**写的太少**。

以我自己为例，我有不少于 10 万行生产环境纯函数式 Scala 编码经验，那些你们在科普文章上看得一知半解的知识（Algebraic Effect / Typeclass / Tagless Final / IO Monad / STM / gADT / New Type 等等），我都已经在生产代码中实践过数万行。

> 而我的本人还是 ADHD（多动症）患者，应试教育的漏网之鱼，高考失败者，仅仅只有大专毕业。我难以专心做一件事超过 5 分钟，也不可能不犯错。

一些代码例子：[https://github.com/mingyang91/doc-man/blob/master/src/main/scala/dev/famer/server/Login.scala#L51](https://link.zhihu.com/?target=https%3A//github.com/mingyang91/doc-man/blob/master/src/main/scala/dev/famer/server/Login.scala%23L51)

我认为编程（包括函数式）本身是实践工程，学习的过程是需要伴随实践的，而不是束之高阁的学院派符号。所以你不能光看科普文，许多科普文章作者本身只是一知半解的新手，写文章用来加深自己理解，其实他们并没有写过几行代码。也不要看论文，那些逻辑符号对你 CRUD 的日常工作用处不大。

-   如果你打开一篇文章，里面在教你如何在 XX 语言中实现 `Functor/Applicative/Monad` 请果断关闭。
-   如果你打开一篇文章，里面列了一堆唬人的逻辑学符号，请果断关闭，你不是这篇文章的目标受众。
-   不懂范畴论，不影响 FPer 写出健壮的函数式代码。就像这世界上大部份程序员不懂 CPU 是如何制造的，依然可以开发大型系统。
-   函数式入门书籍我只推荐一本《SICP》，其他部份请参考所使用的框架/库文档，在实践中学习。

于我而言，函数式很简单，也非常符合直觉。一旦接受了函数式思维以后，你甚至可以简化你的顶层架构设计（例如引入 Reactive Stream），同时用类型来规范（Specification）你的设计，最后用声明式代码去填补空白，只要类型配平了，能通过编译器检验。那么函数式代码的 bug 天然就比指令式代码少一大半，更进一步，你甚至可以使用 Refined/NewType 等技术在编译期把形式化验证也做了。

同时函数式代码可以把你从多线程锁/竞争中释放出来（Fiber/STM/Reactive），使你不再淹没在无尽的状态海洋（ADT）中。就连编解码/序列化这种事情也不需要拖到运行时再去反射，统统编译期确定下来（gADT）。

而如今，还有更先进的指导思想（Algebraic Effect）可以让开发者不再挣扎于各种依赖注入框架，堆砌出几乎无法抽离的耦合代码。

以上这些是科普文章里看不来的，绝知此事要躬行，请开始动手编码，用函数式解决你遇到的任何允许用函数式解决的问题（例如工作中需要执行的一次性事务，迁移脚本，CLI工具等等）。累积一万行编码经验，再回看这个问题，相信你会得出不一样的结论。
