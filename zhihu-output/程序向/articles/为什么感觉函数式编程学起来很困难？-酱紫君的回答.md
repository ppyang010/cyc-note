分清楚手段和目的, 函数式的目的是达到数学上的函数, 也就是纯函数.

所谓纯函数, 就是一次计算, 调用结果永远不变的函数.

为了这个目标, 其他什么 Monad, Continuation, Lazy, Effect, 都只是手段罢了, 殊途同归.

不是说你用 map 就是函数式, 你 map 里有什么 print, random, fs, 基本上就告别函数式的初衷了.

* * *

从编译器角度, 纯函数式更容易分析, 那些高度优化的强编译性语言, 无论 C++ 还是 Rust, Scala还是 Haskell, 其 IR 都是纯函数式的, CPS/SSA/ANF/STG, 统统纯函数式.

哎, 你要说了 C++ 不是过程式语言吗?

**没错, 你发现了你压根没必要追求强行写所谓的函数式代码.**

比如吃饱了没事干把循环强行写成递归, 然后因为递归 0 优化又开始吐槽递归爆栈.

又比如把 `for` 循环改成 `.foreach` 链式调用, 然后因为语言不支持 first-class-continuation 导致没法 `break`, 回头吐槽难用.

听说了个柯里化又把自己的函数全套娃成 `curry(a)(b)(c)(d)`, 然而这东西也是 0 优化, 闭包爆炸, 只是不像递归爆栈一样容易被感知.

知道个 Monad 又在那瞎用, 啥都用 `monad.then().or_else()`, Monad 那么好用那 Haskell 干嘛要发明 do-notation 模拟过程式?

以正统函数式的名义禁用 set, 然后简简单单的 = 变成一堆 update, reduce, 看的人头大. 实际上如果 effect 能内部对消, 那么对外表现仍然是纯函数, 并不违背函数式的原则.

好好的 `class` 不用, 偏要 `const f = () => {}`, 堪称编程史大退化, 记住 closures are the poor man's object, 谢谢.

用蹩脚的手法实现 `effect`, 然后完全不追踪和分析 `effect`, 自作聪明提出了一系列令编译器无语的写法.

* * *

诸如此类, 举着函数式大旗倒行逆施, 把人弄得晕头转向, 把代码弄得编译器无法分析无法优化, 然后靠自己发明一堆蹩脚的手法瞎优化.

**这就是函数式难学的根源, 这就是函数式难优化的根源.**

**没有难度制造难度, 没有问题制造问题.**

-   虚假的函数式布道者: 强行推广一大堆所谓的函数式写法, 带来性能下降, 给函数式招黑.
-   真正的函数式扛把子: 你在教我做事? 过程式, 你只管写, 我全给你改成纯函数式, 性能杠杠的.
