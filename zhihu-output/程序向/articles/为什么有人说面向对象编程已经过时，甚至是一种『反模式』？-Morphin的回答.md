这个东西，你维护过OOP老代码就知道。  
  
大约是在十几年前的时候，OOP教徒写的代码有一个很蛋疼倾向，就是万事皆对象，万事都是可变状态，所有代码的逻辑都是在改变状态上面做文章，甚至会写出那种除了副作用什么都不干的代码。  
  
不说复杂的，就举一个极端简单的例子。比如说你有个类专门用来包裹函数（方法）的返回值，就叫它这个好了。

```text
Result<T>
```

到了函数返回的时候，你可以直接写：

```text
return new Result<T>(xxx);
```

但是很多老法OOP的代码不是这么写的。它在函数一开始会这么搞：

```text
var result = new Result<T>();
```

然后你就会在函数体里面看到到处都是：

```text
result.Value = xxx;
```

最后给你来一个：

```text
return result;
```

而这种玩意重构起来也简单，直接把Result<T>改成不可变数据结构，然后照着编译器报错的地方一个个怼就是了。

这个是不是OOP的问题？其实不是。OOP可没有叫你整天搞状态体操。OOP同样有封装，有只读字段，很多语言里你把初始化函数搞成private都没问题。  
  
但是玄不救非，语法改变不了思维，那种老法OOP的思维，很多就是从GUI编程里面学来的，毕竟OOP+事件驱动状态就是对GUI最直观的抽象，画面加载的时候，把所有东西初始化一下，控件有没有选中，输入框里面写了什么内容，这些都是可变状态，而用户点击了一个什么东西，就把这些状态更新一下嘛。

但你拿着这个锤子到处找钉子，你就会写出result.Value = xxx这种贵物。真实世界里面有很多东西，本质不是状态管理而是计算，这个时候学一点函数式的思维就是很有必要的。比如同样这个问题，能不能用非OOP的方法去解决？能不能把它抽象成映射或者规约？

这算是第二层。

而到了这一层，如果进而发展到拿着纯函数这把锤子到处去找钉子，把状态体操搞成了类型体操，那则是另一个层面的矫枉过正罢了。

编程的本质，是用代码对真实世界交互的抽象。**而一切的抽象都是会泄漏的。**

你的范式决定的，只是漏在哪里。
