这个问题其实已经有非常多的优秀的答案了，按说不应该插一脚。但是还是想从另一个角度来说一下。

  

其实异步这个概念，就有点儿意思。其实当你说出异步这个词的时候，已经意味了一件事情就是你的心流是面向过程的。

也就是说你考虑问题的方式是，先做什么，再做什么，最后做什么。要明白其实程序设计并不只有这一种心流，但是呢这个心流比较贴近计算机（说白了就是一种类图灵机的玩意儿）的工作原理。毕竟计算机就是读取指令然后，至少看起来是按照顺序一条条执行的。

  

如果你的心流变一下，其实这个事情又会变简单，譬如说：

我现在有n件事情要去做，然后每件事情的都有一个前置条件，我把所有要做的事情和它的前置条件都列举出来。然后你们去干就好了，至于你们是同时干还是一个个干，是按照什么顺序干，我并不关心。

但是在这种心流里面，我们并不关心什么同步、异步、并行、并发……

  

所以异步是仅存在于面向过程的这种心流模式的……

异步这个词，说白了就是让我们把过程给切开来，而很多语言并不提供语法上的便利让我们切开过程。这就使得我们需要手动处理很多细节，最常见的做法是：

1、保存现场

2、注册回调方法

3、撰写回调方法并恢复现场

4、继续下面的工作

这其实和CPU处理异步逻辑的方式如出一辙，但是早期的语言并不提供语法上的便利。一个典型的异步过程要写成这样：

```text
fun Begin()
{
  var a,b,c
  //blablabla
  var context = new { a, b, c }
  AsyncCall( End, context );
}

fun End( context )
{
  //blablabla
}
```

其实在这个例子里面，我们还省略了很多关键信息，例如context的类型啥的，在C语言或者类似的语言里面，我们的代码会更啰嗦。

可以看到每一次一个异步调用，我们的代码就必须进行一次割裂。再加上异常传递，上下文的捕获（如HttpContext）等，都需要我们手动去处理，代码量会进一步爆炸：

```text
fun Begin()
{
  var a,b,c
  //blablabla
  var asyncState = new { a, b, c, context = CaptureContext() }
  AsyncCall( End, ErrorHandler, asyncState );
}

fun End( asyncState, errorHandler )
{
  try
  {
    asyncState.context.RestoreContext()
  }
  catch
  {
    errorHandler( error );
  }
}

fun ErrorHandler( error )
{
  //blabla
}

```

再加上异步方法内部还要做安排延续线程等等问题，**代码噪音非常巨大**。

  

那么一定会有人问：**那为什么没有人从语言层面上提供便利来解决这个问题呢？**

  

在我看来这个问题的答案在于：

早期的程序设计语言和基础组件库是**分开来设计**的。

  

比如说上面的例子，我们需要从当前线程捕获上下文，这个上下文一定是通过CaptureContext来捕获的吗？这个方法其实是类库提供的。早期的程序设计语言的理念是，语言和类库是两个东西，或者说语言是类库的基础，类库依托于语言，**而不能反过来，语言依托于类库**。

这是一道**魔咒**，禁锢了程序设计语言设计十数年之久。

  

在语言和类库完全分离设计的前提下，上面的代码已经是最简洁的形式了，因为事实上我甚至都没有涉及到类型。

要彻底解决这个问题，就必须糅合语言和类库，至少要让他们的边界变得模糊。

比如说我们先确定一个特殊的类型叫做ExecutionContext，然后强调所有的异步调用都会自动的调用Capture和Restore方法，这样我们就可以将上文中的context给省去。

然后我们再提供闭包的便利，以便略去asyncState：

```text
fun AsyncFoo()
{
  var a,b,c
  //blablabla


  var continuation = () =>
  {
    try
    {
      //blablabla
    }
    catch
    {
      errorHandler( error );
    }
  }

  var errorHandler = error =>
  {
    //blablabla
  }

  AsyncCall( continuation, errorHandler );
}
```

这里的闭包便利需要另外一个语言和类库的融合就是闭包对象，在C#里面是Delegate实例。在Java里面是SAM接口自动识别。

  

闭包实例如何实现其实也有无数种选择，但是为了在语言层面上实现闭包，我们必须确定其中一种实现的方式，这又在一定程度上将语言和类库进行了捆绑。就像C#如果类库中没有定义Delegate类型，那么所有的委托变量就会报错。而Java中尽管不需要特别的Delegate类型，但是对于SAM接口的特殊对待，也是语言和类库的融合。

值得注意的是，闭包必须要有闭包实例，而像第一个例子中将函数当作参数传递却并不需要，因为函数指针是可以解决这个问题的。但是闭包要求函数和上下文打包，而且是编译器自动打包并且解包，所以是必须要类型配合的。

  

  

其实进化到这个程度，你会发现这个语言已经很像JavaScript了，JavaScript大体上就是这个样子。

  

接下来的进化其实就是程序设计语言和类库的进一步融合，目前的这个样子其实我们仍然无法处理诸如位于循环内部的异步调用。

要解决在任意场景下的异步调用变换，需要语言层面上支持yield，而yield又和IEnumerable实例强绑定，没有这个类型，yield代码无法生成。

要解决异常的传播和返回值的传递，又需要Promise对象支持（在C#里面是Task）。

  

这些都解决后，await就是呼之欲出，水到渠成的事情……

  

  

所以其实整个程序设计语言，或者说面向过程的程序设计语言中的异步调用的关键，在于**程序设计语言必须和类库融合**。

而程序设计语言和类库的分别设计，造就了异步调用在面向过程的心流中必须写成反人类的形式。
