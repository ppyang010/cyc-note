这种月经问题真是月月有人问，年年有人愁。

一律200才是正常用法

\---------------------

http是个缩写，原句是什么？大声说出来。

Hypertext transfer protocol

跟我一起读，超文本 传输 协议

传输协议啊同学们

一个文本传输协议，最多再加一个超文本解释协议，要管那么多？各种业务反馈也要它管？

而且这个里面还有些历史问题

http在设计之初是没有料到现在这个局面的，所以连状态都没有，后来是强行加了cookie和session这一类的东西来存储状态。

http的状态码同理，在设计之初也没想到有人拿来做现在这么复杂的业务，所以大致上把文本处理和两端的文本状态设计了就完事了。到现在其实也不符合我们的业务实际需要了。

我们现在其实是拿http当传输层使用，已经脱离了它原来设想的使用场景，所以原来的一些设计不好用是很正常的。

真要是http原教旨主义者，根本就不应该用json，不应该前后端分离，应该老老实实的从后端传html给浏览器，也不要用http做复杂业务，因为协议根本就不支持那么复杂的状态。

下面这个回答其实讲得特别清楚，我就不展开细说了

[为什么那么多公司做前后端分离项目后端响应的 HTTP 状态一律 200？](https://www.zhihu.com/question/513865370/answer/2358788026)

\---------------------

从系统设计的角度来说，全部200也是先进的做法。

现在前后端的分层都做得很明确，后端的操作系统，容器，http服务器，具体业务服务，一层一层分离得非常清楚，低耦合还运行良好。前端的分层现在其实也在朝这个方向前进。

在保证开销不增长太多的情况下，低耦合的方式才是正确的方式。传输的问题交给传输，业务的问题交给业务。

这个问题下有个回答写得很好

[为什么那么多公司做前后端分离项目后端响应的 HTTP 状态一律 200？](https://www.zhihu.com/question/513865370/answer/2331933561)

不科学做法当然会导致麻烦的结果。作为一个工程技术人员，尊重科学，尊重客观规律是最基本的素养。

不管是http还是restful，把状态码或者什么方法都绑定到具体业务上都是不科学的思路，把简单的东西往复杂方面弄，还没有太多收益。

\--------------------

有人说一律200的人不懂网络。

我觉得这种人才是不懂网络，但凡你在公网上多部署几个系统都不会这么想。

你会想以后的项目一律200好了
