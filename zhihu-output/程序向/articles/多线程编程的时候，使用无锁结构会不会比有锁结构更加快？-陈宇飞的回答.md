无锁的会快，但是多线程网络编程不单单是有没有锁，这里顺便安利一下facebook开源代码里面thrift是怎么做网络io的重点。最早的文章在这里：

[https://code.facebook.com/posts/1468950976659943/](https://link.zhihu.com/?target=https%3A//code.facebook.com/posts/1468950976659943/)  
  

重点讲到的是IOBuf，

> chained memory buffer with views similar to BSD's mbuf or Linux's sk\_buff. In earlier versions of Thrift, the same memory buffer was reused for all requests, but memory management quickly became tricky to use when we tried to update the buffer to send responses out of order.  

你看先说的不是锁不锁的问题，反而先是确保不要复制。malloc里面其实是有锁的，

[多线程编程的时候，使用无锁结构会不会比有锁结构更加快？ - 姚冬的回答 - 知乎](https://www.zhihu.com/question/53303879/answer/134966739)

没提到malloc锁的问题但是提到了忌讳memcpy的问题。但是不管要不要memcpy都是需要一开始的buffer的。Facebook优化这个问题用到了调jemalloc

> To reduce the performance impact of allocating new buffers, we allocate constant-sized buffers from JEMalloc to hit the thread-local buffer cache as often as possible.  

（其实我至今都看不懂jemalloc那些参数怎么调，什么意思。。。）

超过一个IOBuf大小的请求列表连起来

> These buffers are then chained together to become as large as needed, and freed when not needed, preventing some memory issues seen in previous Thrift servers where memory was pooled indefinitely.  

然后最上层Linux api是epoll

现在回到PO主的问题，多线程的还是不多线程的，其实基本上facebook内部网络层面的代码都是多线程的，但是为了让多线程的代码容易维护，会用到**无锁的SPSCQueue 或者MPMCQueue**来确保代码不要到处乱飞（其实MPMCQueue还是有锁的，只是不在critical path上面，代码转在这里

[https://github.com/facebook/folly/blob/master/folly/MPMCQueue.h](https://link.zhihu.com/?target=https%3A//github.com/facebook/folly/blob/master/folly/MPMCQueue.h)

。）

是quora上面Queue了讨论，里面有细讲各种queue的实现以及效果，我不多说，我说多线程在这里是怎么做的（源代码和文档在这里

[facebook/fbthrift](https://link.zhihu.com/?target=https%3A//github.com/facebook/fbthrift/blob/master/thrift/doc/Cpp2.md)

）

\- 你有一堆只负责io的线程，就负责往mpmcqueue里面吧linux 的buffer变成iobuf，以及各种公司内部的逻辑（我记得还有加密一定是在io做的，deserialization不记得是不是了）

\- 你有负责你自己业务逻辑的线程，这些线程就是从mpmcqueue里面拿东西，然后执行你的逻辑

\- io线程再负责把结果仍回去
