# 如何充分利用榨干你的Codex

大多数开发者最初使用编程 Agent 的场景都是代码相关的工作：检查代码仓库、做 diff、运行测试、打开 Pull Request。

这只是 Codex 的核心重心。但电脑上大量工作其实已经通过代码来完成了：执行 shell 命令、浏览网页、调用 API、导出文档、响应事件、触发自动化。当这些能力逐渐开放给 Codex 时，它开始不再像一个狭义上的"编程助手"，更像是一个完成电脑工作的系统。Codex 应用让这个转变变得具体。一个 Thread 可以保持上下文、使用工具、生成制品、在多次提示中持续运行，而不会在每次交换后重置。

想要更多地利用 Codex，意味着把这些能力组合起来使用：

-   • 持久的 Thread，保持上下文
    
-   • 语音、掌控（Steering）和队列（Queuing），让用户在关键环节保持参与
    
-   • 浏览器、电脑使用、MCP 服务器和连接器，让 Codex 在代码仓库之外行动
    
-   • Thread 自动化和 Goals，让用户在离开时也能继续工作
    
-   • 侧边栏，用户可以在那里审查代码、文档、幻灯片和其他制品
    

## 持久的 Thread

> 持久的 Thread：长期运行的 Codex Thread，在多次会话中保持工作上下文。

置顶 Thread 是保持持久 Thread 的一种方式。它们对重复性工作流很有用，例如：

-   • 首席助理 Thread
    
-   • 发布 Thread
    
-   • 文档审查 Thread
    
-   • 专用于外部监控的 Thread
    

这些是持久的工作空间，而不是短对话。Codex 可以随时间推移重新访问它们，保留先前的决策、偏好和工作上下文——否则这些每次都要从头重建。

置顶 Thread 快捷方式让这变得实用。Command-1 到 Command-9 可以直接跳转到已保存的 Thread。

## 语音输入

语音输入之所以有价值，是因为它能在想法被压缩成精心润色的文字之前捕捉到粗糙版本。

Codex 内置语音输入。它特别适合那些说起来很自然但打字却很别扭的模糊起点：

> 我觉得有人在 Slack 里提过一个叫 Ben 的人。  
> 我不记得细节了。  
> 请帮我查一下。

对于可以搜索、收集上下文并报告结果的 Agent 来说，这通常就够了。

对于一个两三分钟的思想倾诉也很好——在任务完全成型之前。

文字记录也是如此。原始的会议记录或口述的计划笔记往往比简短的摘要提供更好的素材，因为它保留了不确定性、重点和未完成的思路。

## 掌控（Steering）和队列（Queuing）

语音与对活动的明确控制结合使用时更有价值。

> 掌控（Steering）：在当前步骤完成之前，用新的方向打断进行中的 Codex 任务。

-   • 把这个弄小一点
    
-   • 这两个元素之间的间距感觉不对
    
-   • 这段文字错了
    

> 队列（Queuing）：在工作完成后为 Codex 添加任务。

队列（Queuing）则不同。它不会打断正在进行的任务，而是把下一个任务加入队列。用户可能会说：

> 工作完成后，把预览链接发到 Slack 给审查人。

掌控（Steering）改变 Codex 现在正在做的事。队列（Queuing）改变接下来应该发生什么。两者都让用户在工作时保持密切参与。

## 随时随地工作

Codex 移动应用

> \[7\]

改变了用户必须待在桌前的场景。任务可以在一台 Mac 上开始——那里有文件、权限和本地设置——然后用户在手机上继续跟进。本地环境保持不变；用户不必切换。

这在碎片时间很重要。用户可以在 Codex 运行较长任务时离开桌子，在外面时回答问题，批准下一步，或者在回来之前引导 Thread。

## 自动化

自动化（Automations）

> \[8\]

按计划运行 Codex 工作。定期任务应该从工作区全新开始时使用计划的自动化，例如每日报告或常规代码仓库检查。当计划应该回到有运行上下文的活跃对话时使用 Thread 自动化。

> Thread 自动化：心跳式定期唤醒，返回到同一个 Codex Thread 按计划运行。

置顶 Thread 有用，但它们仍然等待用户回来。Thread 自动化可以每隔几分钟或几小时检查一次，持续到满足某个条件，并随着时间调整节奏。

首席助理 Thread 可以每 30 分钟运行一次：

> 每 30 分钟检查 Slack 和 Gmail 中需要我注意的未回复消息。  
> 帮我优先处理最重要的事项。  
> 如果有人问我一个问题，深入研究答案并起草回复，但不发送。

当用户回来时，收集上下文最昂贵的部分往往已经完成。人类仍然决定什么会被发送。

Thread 自动化也适合反馈循环。Thread 自动化可以监视 Pull Request 评论、Google Docs 评论或 Slack 回复，并在用户离开时保持周围的工作进行。

想象一个动画工作流：审查人在 Slack 中分享视频。Thread 自动化可以按计划检查 Thread，在评论到达时渲染新版本，并在同一 Thread 中回复并标注审查人。如果一个集成无法完成最终上传，桌面自动化可以通过 GUI 完成最后一步。

循环跨越 Slack 收集反馈、代码仓库进行渲染，以及桌面自动化完成最终上传。

## Goals

当任务有真实的终点线、Agent 可以持续推进时，Goals 最强大。弱目标的例子：

> 在这个 Markdown 文件中实现这个计划。

更强的目标有可衡量的成功标准。

例如，工程师可能通过设置新目录、定义目标、明确终点线将内部工具从 Python 迁移到 Rust：新实现直到单元测试通过才算完成。

Goal 结合了持续执行和验证器。用户定义结果、停止条件，以及判断 Codex 是否正在接近目标的信号。

有用的验证器包括：

-   • 测试套件
    
-   • 基准测试
    
-   • Bug 复现
    
-   • 验证矩阵
    
-   • 必须持续通过的端到端工作流
    

雄心很重要，但没有验证就只是愿望。

## 侧边栏

侧边栏

> \[9\]

让工作在产生它的对话旁边进行。不必导出制品和切换上下文，用户可以直接在原地审查。输出可能是代码，但也可能是幻灯片、PDF、网页、表格或其他沿途创建的制品。

它在四种工作中特别有用：

1.  1\. 检查制品
    
2.  2\. 标注需要更改的地方
    
3.  3\. 操作网页表面
    
4.  4\. 审查变更
    

侧边栏让用户直接在原地审查 Markdown、电子表格、数据表格、文档和幻灯片。他们可以在不中断循环的情况下检查、标注和修改制品。

AnnotationsSheets in Codex让 Codex 检查渲染后的页面、控制它，并直接在审查中的表面响应标注。页面或制品上的评论留在工作循环内，而不是成为单独的交接。。它们为偏好、重复工作流和已知陷阱提供本地召回层。它们补充了明确的书面上下文，而不是取代它。Chronicle以同样的方向推动，帮助 Codex 从最近的屏幕上下文构建记忆。
