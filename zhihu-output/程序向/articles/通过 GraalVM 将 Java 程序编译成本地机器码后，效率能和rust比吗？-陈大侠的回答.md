有两个项目 用过 graalvm的 native-image AOT编译项目，说说感受吧

首先说和jit java的性能对比，内存是实打实的变小了，无论是workingset还是private bytes，都会比jit启动的java用的少，但是我个人的感觉是，程序运行的速度是变慢了，而且是肉眼可见的慢。

我有一个常用的excel管理软件用gvm aot编译的，和 jre8 的 jit的相比，加载300张excel表格，速度明显比jit的慢，并且打开20000行以上的表格，有明显的卡顿掉帧现象，而jit的不会有。

另外关于垃圾收集，gvm官方给出这样的说明

*\--gc=<value>: select Native Image garbage collector implementation. Allowed options for <value> are: G1 for G1 garbage collector (GraalVM Enterprise only); epsilon for Epsilon garbage collector; serial for Serial garbage collector (default).*

aot编译社区版的只支持 Serial GC，企业版才有G1。

这就搞笑了，我花了钱还只能用快过时的G1，用jit版本上用免费且更先进的

Shenandoah 和 ZGC不香吗

另外，现在java aot的性能连自家的jit都打不过，怎么去打rust和c/c++们

有一个点我感觉很多人都不知道，c/c++性能好不是因为aot编译，而是因为手动管理内存，这一点从go的性能就能看的出来，go是正儿八经aot出生，有听过他性能比赶上c++的说法吗？甚至连赶超java都没听说吧！

我看到在用gvm aot编译的时候会用到cl.exe这种微软的c++编译器，想来应该先把java代码转换成c/c++代码，然后再用c++编译器编程成本地程序（不知道对不对）。这种方法虽然编译的是c++代码，但是这种代码也是自动管理内存的（类似unity上的iltocpp），性能并不会比jvm上运行的java好，而c/c++性能好是因为手动管理内存。

手动管理内存意味着你在堆上分配一个块内存，你要负责他的整个生命周期，直到手动销毁，这对程序员负担很重，容易出错。

随着自动管理内存的编程语言流行，编程变的简单了，但是性能一言难尽。就说java把，随着版本的迭代，出现各种垃圾收集器，就是为了提高自动管理内存的性能。

java程序员都知道，java进程起来，就肯定会分配出几个线程来用于垃圾收集工作，从最开始的单线程收集，到后面的多线程。最开始的stw时间长，到后面的stw时间短，算法越来越先进，但是机制也越来越复杂。像cms、 g1、zgc这种低停顿收集器，极尽各种手段来缩短stw时间，但是stw以及之外的各个预收集阶段，都在悄无声息的消耗着CPU。这些收集算法要负责管理对象的引用链，还要把分代年龄写到每个对象的对象头上，还要把内存区域设计成利于GC算法运行的结构，这些都是很重的负担，但是在c/c++中却都不需要。这就是c/c++比java快的原因，在没有技术突破前，永远绕不过去。

对于性能而言，吞吐量是一个很重要的指标，自动管理内存在吞吐量上永远赶不上手动管理内存，知道这点，其实就能知道java类技术，包括aot的java，永远摸不到c/c++的门槛。

graalvm的优点目前我只看到了节省内存、启动速度快、代码不会泄漏这3点外，其他真没看到好处。另外，我参与的一个项目，需要把开发的软件给别的公司用，但是又不想代码被他们看到，所以才用了aot编译。至于省内存、启动速度快这种，其实都可有可无

至于gvm aot的问题，那属实有一大堆，随便说几个

-   编译速度非常慢，比javac编译慢了上百倍都不止，等的心焦
-   处理反射麻烦的很。每次正式编译前，都要用特殊的指令跑下程序，把反射代码都跑到，生成反射配置，然后才能编译出正确的程序
-   带asm之类的动态生成字节码的技术不能用
-   编译GUI程序尤其麻烦，需要用第三方魔改gvm，比如gluonfx。而且编译出来还有各种问题比如awt支持不好，麻烦的要死
-   没法用arthas之类工具排查问题
-   参考资料很少

说实话，用java技术，如果不是不想给别人看到代码，如果光是自己服务器上部署，肯定不会去用这种技术
